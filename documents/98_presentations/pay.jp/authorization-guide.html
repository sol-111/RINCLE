はまりポイント集（よくあるミス）

1

capture=false の指定忘れ

CRITICAL 
// NG: capture パラメータなし（デフォルト true = 即時課金！）
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  currency: jpy

// OK: capture=false を必ず指定
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  currency: jpy
  capture: false

被害: お客さんの予約確定時に即座にお金が引き落とされる。

対策: Bubble のワークフローで capture に false をハードコーディング。

2

charge_id の保存忘れ

CRITICAL 
// NG: charge_id を保存しない → キャプチャできない！
  オーソリ実行 → レスポンス受け取る → 保存しない

// OK: レスポンスの id を即座に保存
  オーソリ実行 → レスポンスの id → 予約の charge_id フィールドに保存

被害: キャプチャ不可 = お金を回収できない。最悪のシナリオ。

!
実際にこのバグが起きている！
現行システムの延長決済で __charge_id の保存漏れが発生中。延長分の返金ができない状態。同じミスを絶対に繰り返さないこと。
3

expiry_days の上限は60日

HIGH 
expiry_days: 90    ← 60日を超える値は無視される
expiry_days: 60    ← 最大60日

被害: 予約日が60日以上先だとキャプチャ時に失効済み。

対策: 営業カレンダーの予約可能範囲を60日以内に制限する。

4

海外カードのオーソリ有効期限は7日！

HIGH
カード種類expiry_days 上限
日本発行カード最大60日
海外発行カード最大7日

確認方法: テストカード 4000000900000003（is_jp=false）で検証可能。

5

キャプチャ時の金額変更に要注意

HIGH
条件結果
キャプチャ金額 ≤ オーソリ金額OK
キャプチャ金額 > オーソリ金額NG（エラー）
// 推奨パターン: 延長分は別チャージ
  予約時:     オーソリ 10,000円   (charge_id = ch_001)
  ライド開始: キャプチャ 10,000円 (ch_001 をキャプチャ)
  延長発生:   新規課金 3,000円   (capture=true で別チャージ ch_002)
6

テスト環境で本番キーを使わない

CRITICAL 
// NG: テスト時に sk_live_xxxx を使う
→ テストカードが使えない！ 本物の課金が走る！

// OK: テスト時は sk_test_xxxx / pk_test_xxxx を使う
→ テストカードが使える、本物の課金は発生しない
7

オーソリ失効後のキャプチャ

HIGH 
5月1日: オーソリ（expiry_days=60）
7月5日: キャプチャ（65日後） → エラー!

5月1日: オーソリ（expiry_days=60）
6月25日: キャプチャ（55日後） → 成功

対策: キャプチャ前に GET /v1/charges/{id} で状態確認。失効済みなら再オーソリ。

8

二重キャプチャ

MEDIUM

対策: キャプチャ前に payment_status を確認し、"authorized" の場合のみ実行。ボタンの連打防止も設定。

9

Platform API での tenant 指定忘れ

HIGH

RINCLE は Marketplace型の Platform API を使っているため、tenant と platform_fee は常に必須。

10

Webhook の charge.captured イベント

MEDIUM

即時課金でもオーソリ→キャプチャでも charge.captured は発火する。区別が必要な場合は独自の payment_status で管理すること。

テストシナリオ

A 正常フロー（オーソリ → キャプチャ）

  1. テストカード 4242424242424242 でカード登録
  2. 予約を作成・確定 → オーソリ実行
  3. 確認: charge_id が保存、payment_status が "authorized"、Pay.JP管理画面で captured=false
  4. ライド開始 → キャプチャ実行
  5. 確認: payment_status が "captured"、Pay.JP管理画面で captured=true

B キャンセルフロー（オーソリ → 解放）

  1. 予約を作成・確定（オーソリ実行）
  2. 予約をキャンセル
  3. 確認: payment_status が "cancelled"、Pay.JP管理画面で refunded=true

C カードエラーフロー

  1. テストカード 4000000000080319 でカード登録（登録自体は成功）
  2. 予約を作成・確定 → オーソリ実行 → card_declined エラー
  3. 確認: エラーが分かりやすく表示、予約がキャンセルまたは保留、charge_id は未保存

D 延長決済フロー

  1. 正常フローでオーソリ → キャプチャまで完了
  2. 延長操作を実行
  3. 確認: 延長分は別の charge_id で新規課金、__charge_id に保存済み、返金が可能

チェックリスト

実装前チェック

  • テスト環境の API キーが sk_test_ / pk_test_ であることを確認
  • API Connector に Charge_capture（キャプチャ用）を追加した
  • Charge_by_car_id に capture と expiry_days パラメータを追加した
  • 予約テーブルに payment_status フィールドを追加した

実装中チェック

  • 予約ワークフローで capture=false を指定している
  • 予約ワークフローで expiry_days=60 を指定している
  • オーソリ成功後に charge_id を予約に保存している
  • オーソリ成功後に payment_status を "authorized" に更新している
  • ライド開始ワークフローで Charge_capture を呼び出している
  • キャプチャ成功後に payment_status を "captured" に更新している
  • キャンセル時の条件分岐（authorized / captured）が正しい
  • 延長料金は別チャージで処理している（オーソリ金額を超えない）
  • tenant と platform_fee を必ず指定している

テスト完了チェック

  • シナリオ A（正常フロー）が成功する
  • シナリオ B（キャンセルフロー）が成功する
  • シナリオ C（エラーフロー）でユーザーに分かりやすいメッセージが出る
  • シナリオ D（延長決済フロー）が成功する
  • Pay.JP 管理画面で charge の状態が正しいことを確認
  • 海外カード（4000000900000003）でのテストを実施

リリース前チェック

  • API キーを本番キー（sk_live_ / pk_live_）に切り替えた
  • 営業カレンダーの予約可能範囲が60日以内に制限されている
  • エラーメッセージがユーザーフレンドリーであることを確認
  • 管理者へのエラー通知が設定されている
