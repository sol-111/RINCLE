## クライアント指定リファレンス

### Honda GO Bike Rental
- URL: https://hondago-bikerental.jp/
- クライアントコメント: 「店舗、バイクのリスト表示、会員登録などみやすくモバイルのUIなどは理想」

**RINCLEと同じ構造のサービス。最も直接的な参考。**
- 全国400店舗以上のHonda販売店ネットワークでバイクレンタル（= プロショップネットワーク型）
- 検索: 都道府県→市区町村→店舗の3段階カスケード + 排気量/車種名フィルタ + 地図/現在地検索
- リスト表示: グリッドレイアウトのカード形式（排気量バッジ/車種画像/車名/説明）
- 料金シミュレーター: 独立5ステップ。クラス→車種→期間→保険→装備でリアルタイム見積
- 予約: 5ステップ（店舗・日時→オプション→情報入力→確認→完了）。プログレスバー明示
- 会員登録: 3ステップ（メアド送信→本登録→完了）。入会金・年会費無料
- 料金表: 6時間プラン×7排気量クラスの明確なマトリクス
- 「はじめての方へ」: 予約→来店→利用→返却の4ステップを図解
- レビュー機能: なし
- レスポンシブ対応（PC/SP出し分け）

**学ぶべきポイント:**
- 料金シミュレーターのリアルタイム見積UI
- 料金表のマトリクス表示（時間×クラス）の明快さ
- 「はじめての方へ」の4ステップ図解
- 保険・補償の比較UI（3シナリオ並列比較）
- 5ステップ予約フローのプログレスバー（1ステップあたりの項目数を絞る設計。「項目数>ステップ数」原則と整合 → 後述の定量ベンチマーク参照）

## 海外バイクレンタルの先行例（商材が同じ直接参考）

### BikesBooking.com — 「集約型OTAの信頼設計」の教科書
- URL: https://bikesbooking.com/en/
- 構造: 70カ国対応の世界最大級バイク（自転車・スクーター・モーターサイクル）レンタル予約OTA
- **RINCLEとの類似度: ★★★★☆**（商材が同じ。横断検索・比較・予約のモデルも一致）

**学ぶべきポイント:**
- 検索フォームは**国→都市→日時→車両タイプの4項目のみ**。コンセプトも「①比較して見つける→②オンライン予約→③受け取るだけ」の3ステップで提示
- **信頼指標の多層配置**: ベストプライス保証 / 保険全車標準付帯 / ほとんどの予約でキャンセル無料 / 検証済みレビュー をファーストビューに並べる
- **「予約した車種そのものが用意される」保証**（レンタカーの「クラス指定」とは違う点）→ 車種指名性が高いスポーツバイクで特に効く訴求

### listnride — 「CSR+静的SEOページ別建て」の生きた先行例
- URL: https://www.listnride.com/
- 構造: 欧州中心のC2C/B2C混合自転車レンタル（8万台以上・1,000ロケーション以上）。リクエスト→オーナー承認型の予約

**学ぶべきポイント:**
- **`/都市名/車種カテゴリ`（例: `/mallorca/road`）の静的SEOページを大量生成**。トップはJSレンダリングの重いCSR構成だが、静的LP群が別途インデックスされ検索流入を確保 → RINCLEの「Bubble+静的LP別建て」戦略の実例（アソビューも同じ構図）
- レビューには**個人オーナー車両の整備品質ばらつき**（危険なハンドル等）への不満が実在（[Trustpilot](https://www.trustpilot.com/review/listnride.com)）→ 裏返しがRINCLEの差別化軸「**全車プロショップ整備済み**」。信頼指標の筆頭に置くべき
- リクエスト承認型は柔軟だが摩擦が大きい → 在庫を自社DBで持つRINCLEは**即時確定予約**で優位に立てる（Anycaのクイック予約と同じ訴求）

## 予約フォーム・予約フローの定量ベンチマーク

### CVRを決めるのは「ステップ数」ではなく「フォーム項目数」
- ECチェックアウトの平均は11.3項目だが、ほとんどのサイトで実際に必要なのは**8項目**（[Baymard](https://baymard.com/blog/checkout-optimization-from-16-fields-to-8)）
- リードフォームのCVRは 1項目18.2% → 8項目5.8% → **9項目以上4.2%（約1/4に低下）**（[NeilPatel](https://neilpatel.com/marketing-stats/conversion-rate-by-form-fields/)）
- ただし「分割」は有効: マルチステップ+プログレスバーはシングルステップより約14%高く変換（[Venture Harbour](https://ventureharbour.com/how-form-length-impacts-conversion-rates/)）
- **→ RINCLEの予約フォーム仕様: 「合計8項目以下 × 2〜3ステップ + プログレスバー」**。Honda GOの5ステップは項目をステップに分散しているから成立している

### ゲストチェックアウトと会員化のタイミング
- 「アカウント作成の強制」はカゴ落ち理由の**23〜26%**。撤廃でCVR **20〜30%向上**（[Baymard](https://baymard.com/learn/checkout-flow-ux-optimization)）
- Baymard推奨パターン: **会員化は予約完了画面で提案**する。予約情報を自動入力済みにし「パスワードを設定するだけ」にする
- RINCLEの現実解（本人確認・免責同意が必要なため完全ゲストは不可）: 予約時は「メール+氏名+電話（+身長/サイズ）」の最小限 → 残りは来店前の事前チェックインへ後送り → 完了画面で会員化を提案、の3分割

### 予約放棄と回収メール
- 旅行業界の放棄率は81〜84.6%（業界最高水準）。最大の離脱点は「**総額が表示された瞬間**」→ コミコミ総額を検索結果カードまで前倒しする根拠
- 放棄者の87%は再検索意向があり、**46%は24時間以内に再検索**（[Econsultancy](https://econsultancy.com/why-do-people-abandon-online-travel-bookings/)）
- 回収メールの定石: ①放棄1時間以内に1通目（予約内容の保存リンク+空き残数）、②翌朝に2通目（別車種・別店舗・別日の代替提案）。旅行業界のカゴ落ちメールは開封44.1%/クリック11.6%（[diggintravel](https://diggintravel.com/shopping-cart-abandonment-emails-travel/)）
- メールアドレス取得前の放棄には打てない → **お気に入り・検索条件保存（メール登録つき）が回収メールの前提インフラ**
- KPI初期目標の目安: 旅行・ホスピタリティ平均CVRは2.7%（モバイルはデスクトップの半分以下が業界標準）→「訪問→予約完了2%台」「予約開始→完了25〜30%」が現実的な比較基準

## レビュー収集UXのベストプラクティス

- 投稿レビューの**約70%は依頼メール経由** → 「待ち」では集まらない
- 体験型サービスの依頼最適タイミングは**体験完了の24〜48時間後**（商品ECの「7〜14日後」とは異なる）（[ExpertReputation](https://expertreputation.com/best-practices-for-timing-your-review-requests-email-sms-and-in-app/)）
- **写真付きレビューはCVR+26%、UGC画像は企業画像の12倍の信頼性**（[NaviPlus](https://naviplus.dgbt.jp/info_review.html)）
- 依頼文は60語（日本語なら100〜150字）以内が最も回答率が高い。リマインドは5〜7日後に1回まで、2通超は逆効果（[WiserReview](https://wiserreview.com/blog/review-request-email/)）
- 段階インセンティブ（写真+50pt / 200文字以上+50pt 等）が国内ECの定番。ただし**「高評価を条件にした特典」は景表法・規約違反**。インセンティブは投稿行為そのものに付与する。Googleレビューへのインセンティブは規約で全面禁止（自社サイト内レビューのみ可）
- **RINCLE推奨の3点セット**: ①返却時に店頭QR/タブレットでその場依頼（記憶・感情のピーク）→ ②翌朝メール（短文+投稿ボタン1つ）→ ③5〜7日後に1回だけリマインド。VELTRA型の写真付きポイント還元を併用。コールドスタート目標「各店5件・計120件」の達成手段として最重要

## Bubble.ioでの実装可能性

RINCLEはOTAと違い**在庫データを自社DBで完結して持てる**（外部カレンダー同期が不要）ため、Bubble実装の難易度は低い。主出典: [lowcode.agency 旅行マーケットプレイス構築ガイド](https://www.lowcode.agency/blog/build-travel-marketplace-with-bubble)

| 機能 | 実装可能性 | 方式 |
|---|---|---|
| 検索バー（エリア×日付×車種） | ◎ ネイティブ | DB検索+制約。24店舗（2026-08-20実測では56店舗）・数百台規模なら標準機能で十分 |
| カレンダー空き表示（残数つき） | ◎ プラグインで定番 | Availabilityレコード+カレンダーUI（Booking Slots等） |
| 空き状況の一覧横断比較 | ○ 可能だが要設計 | 「予約済みレコードを除外」方式 |
| 自転車比較（2〜3台横並び） | ◎ ネイティブ | カスタムステート+リピーティンググループ。プラグイン不要 |
| 地図検索 | ○ | Google Maps/Mapboxプラグイン。車両単位でなく店舗単位ピンに限定 |
| レビュー（実利用者のみ投稿） | ◎ ネイティブ | 予約レコード紐づけで担保 |
| 放棄回収メール / ゲスト予約 | ○ | Backend Workflowでスケジュール送信 / メールのみの一時レコード |
| 決済（与信→キャプチャ、店舗送金分配） | ◎ | Stripe / Stripe Connect |
| SEO・初回表示速度 | ✕ 構造的に弱い | 静的LPの別建て（既存提案どおり）。listnrideが先行例 |

**最大の地雷は「日付範囲をまたぐ空き検索」のDB設計**。「5/24〜5/25に空いている全車両」の検索は、データ構造を誤ると後で作り直しになる。推奨は「予約済みレコードを除外する」方式だが、`:filtered (advanced)` はクライアントサイド処理のため件数増に弱い（[Bubble Forum](https://forum.bubble.io/t/calendar-availability-and-booking/277695)）。**Tier 1の検索バー実装前に、DB再構築後の新設計（2026年7月に本番リリース済み）と整合を取りつつDB設計をレビューすること。**
