0. これから何を作るのか

ポイント: BubbleとWordPressは別々の場所で動いている（BubbleはBubble社、WordPressはX-Server）。だから入口に「交通整理係」を1枚かませる。それが Cloudflare。

現状（今）

rincle.co.jp は全部Bubbleに向いている。WordPressはまだ無い。メール送信だけ別系統でSendGridを使用。

✅

なぜP2で落ちないか

Cloudflareに"今と同じレコード"を先にコピーしてあれば、新旧どちらのDNSを読んでも同じ答え（Bubble）→ 気づかれず無停止。だから「コピー→NS切替」の順が鉄則
⚠️

唯一のリスク = P3のオレンジ化

/blog 振り分けには rincle.co.jp をCloudflare経由(オレンジ)にする必要があり、その瞬間に二段重ねの真価が問われる。崩れてもオレンジ→グレーに戻せば数秒〜数分で即復旧

ゼロダウンタイムにするコツ

  1. 1
    P2でレコードを完全ミラーしてからNS切替（落とさない大前提）
  2. 2
    NS切替前にTTLを短くしておく（反映も戻しも速い）
  3. 3
    P3のオレンジ化はアクセスの少ない夜間にやる（万一の影響を最小化）
  4. 4
    崩れたら即グレーに戻す
※ 6/19で話した「リリース時に夜間1h停止」はDB再構築の話。このブログ基盤の作業は原理的にrincleを止めずにやれる（止めるとしてもP3を安全に試すための短時間で、必須ではない）。
PHASE0

事前バックアップ・DNS棚卸し

リスク 低

NSをCloudflareに引っ越すと、今X-Serverに登録されているDNSレコードを全部Cloudflareに移す必要がある。1件でも漏らすと、その機能（特にSendGridメール送信）が止まる。

  1. 1
    X-Serverの管理画面でDNSレコードを全件控える（DNSレコード設定 → rincle.co.jp → A/CNAME/MX/TXT 全部）。digでは見えないSendGrid固有のCNAME（em####・url####）が必ずあるので管理画面で実物確認
  2. 2
    特に必須で控える：A（root・www→Bubble）／SendGrid系（s1/s2._domainkey・em####・url####）／SPF（TXT）
  3. 3
    SendGrid側でも Settings → Sender Authentication で「必要なDNSレコードの正解リスト」を確認（移行後の答え合わせ用）
💡 Cloudflareは移管時に既存レコードを自動スキャンして取り込むが100%ではない。だから手動の棚卸しリストと突き合わせる。
PHASE1

X-ServerにWordPressを設置（まず単体で）

リスク 低戻せる: 容易

いきなり /blog/ に組み込まず、WordPress単体が動く状態を先に作る。問題の切り分けがしやすい。

1-1. 置き場所（origin）を決める

リバースプロキシで「実体を取りに行く先」を origin（オリジン） と呼ぶ。専用ホスト名を用意する：

  • wp-origin.rincle.co.jp を作り、X-Serverのサーバーへ向ける
  • このホスト名は後でCloudflare上ではDNS only（グレー雲）にする（Cloudflareを通さず直接X-Serverへ＝二段重ね回避）

1-2. インストール

  1. 1
    X-Server パネル → 「WordPress簡単インストール」
  2. 2
    インストール先: wp-origin.rincle.co.jp の /blog ディレクトリ（公開URLが /blog/ なのでoriginも揃える）
  3. 3
    SSL: X-Serverの無料独自SSL（Let's Encrypt）を wp-origin.rincle.co.jp に発行
  4. 4
    https://wp-origin.rincle.co.jp/blog/ でWordPress初期画面が出ることを確認
この時点では「WordPressが単体で見える」だけでOK（rincle.co.jp/blog/ ではまだ見えない）。
PHASE2

NSをCloudflareへ移管

リスク 中戻せる: NSを戻す
📌 考え方: これはレコードを「削除」する作業ではなく、ドメインの案内所（NS）を“引っ越す”作業。
  • 鉄則の順序: ①全レコードを先にCloudflareへコピー → ②最後にNSを切り替える。逆だとサイト・メールが一瞬切れる
  • 切替後、X-Server側の旧レコードは手で消さなくてOK（NSがCloudflareを向いた時点で自動的に無効化。切り戻し用に残すのも可）

2-1. Cloudflareにドメインを追加

  1. 1
    Cloudflareアカウント作成（弊社管理・無料）→「Add a site」→ rincle.co.jp → Free プラン
  2. 2
    Cloudflareが既存DNSを自動スキャン → Phase 0の棚卸しリストと1件ずつ突き合わせ、漏れを手動追加
    • A（root・www → Bubble）: 雲はPhase 3に合わせ基本オレンジ（プロキシON）
    • SendGrid s1/s2._domainkey・em#### CNAME → 追加・グレー（DNS only）
    • SPF（TXT） → そのままコピー
    • wp-origin.rincle.co.jp（A → X-Server IP）→ 追加・グレー（DNS only）
⚠ DKIM等メール認証系のCNAME/TXTは必ず「DNS only（グレー雲）」。プロキシ（オレンジ）にすると値が書き換わり認証が壊れる。

2-2. NSをX-Server → Cloudflareに変更

  1. 1
    Cloudflareが指定する2つのネームサーバー（例 xxx.ns.cloudflare.com）を控える
  2. 2
    X-Server の「ネームサーバー設定」で、X-ServerのNS → Cloudflareの2つに置き換える
  3. 3
    反映に数時間〜最大48時間。Cloudflare管理画面が「Active」になれば完了
✓ Phase 2 の動作確認（Phase 3前に必須）
  • rincle.co.jp が今まで通りBubbleで表示される（＝二段重ねでもサイトが生きている）
  • SendGridのメール送信が正常（テスト送信で届く・迷惑メール判定なし・DKIM pass）
  • https://wp-origin.rincle.co.jp/blog/ でWordPressが見える
ここで rincle.co.jp が表示されない＝二段重ね（orange-to-orange）問題。対処はPhase 3冒頭の検証チェックポイント参照。
PHASE3

/blog/* をWordPressへ振り分け

リスク 中戻せる: ルール削除

★ 3-0. 二段重ね（orange-to-orange）の検証チェックポイント

Phase 2-3で Bubble が表示されていればクリア。表示されない/エラー（1000番台等）の場合：

  1. 1
    Bubble側: Settings → Domain/email で rincle.co.jp が正しく登録されているか
  2. 2
    解決しないなら Bubbleサポートに「Cloudflare経由でアクセスしたい」旨を問い合わせ（CNAMEターゲット案内 or ドメイン許可）
  3. 3
    どうしても無理なら フォールバック＝サブドメイン方式（blog.rincle.co.jp をWordPressにCNAME直結。交通整理不要・SEOは少し弱まるが確実）
このチェックを越えられるかが本構成の成否。ここは時間を取って検証する。

3-1. Origin Rule で /blog/* をWordPressへ

Cloudflareの Origin Rules＝「URLのパスに応じて取りに行く先(origin)を上書き」する機能。Workerより簡単で今回はこれで十分。

  1. 1
    Cloudflare → Rules → Origin Rules → Create rule
  2. 2
    条件: URI Path starts with /blog
  3. 3
    アクション: Override origin → Host を wp-origin.rincle.co.jp に上書き（必要に応じSNIも合わせる）→ 保存
代替: 詰まる場合は Cloudflare Worker でも実現可（if (path.startsWith('/blog')) fetch(WordPress) else fetch(Bubble)）。

3-2. SSL設定

  • Cloudflare → SSL/TLS → 暗号化モードを Full（または Full strict）
  • origin（X-Server）側にも有効なSSL証明書が必要（Phase 1で発行済み）。無いと Full strict でエラー
✓ Phase 3 の動作確認
  • https://rincle.co.jp/blog/ でWordPressが表示される
  • https://rincle.co.jp/ など他ページが今まで通りBubble
  • 鍵マーク（SSL）が両方で有効
PHASE4

WordPressを /blog/ 配下で正しく動かす

リスク 中戻せる: 設定変更

WordPressは「自分が rincle.co.jp/blog/ で公開されている」と知らないと、リンクや画像のURLがズレる。これを直す。

4-1. サイトURLの設定

管理画面 設定→一般 で設定可。ただしログイン不能リスクがあるので先に wp-config.php に直書きが安全：

define('WP_HOME', 'https://rincle.co.jp/blog');

4-2. パーマリンク

設定→パーマリンク→「投稿名」など（/blog/%postname%/）→ 保存（ルール再生成）。

4-3. リバースプロキシ越しの定番対応

    if (!empty($_SERVER['HTTP_X_FORWARDED_PROTO']) && $_SERVER['HTTP_X_FORWARDED_PROTO'] === 'https') {
    $_SERVER['HTTPS'] = 'on';
}

付録：Cloudflareとは／なぜX-Serverではダメか

Cloudflareとはどんなサービスか

ひとことで言うと、サイトの“正面入口”に立つ多機能スタッフ。ユーザーとサーバーの間に入り、全アクセスがまずCloudflareを通ってから本体に届く位置にいる。世界の多くのサイトが使う定番で、無料から使える。

Cloudflareができること何屋さん
DNS管理ドメインの「案内所」（名前→サーバーの変換）
リバースプロキシ／ルーティングアクセスの「交通整理係」（パスで行き先を振り分け）
CDN・キャッシュコンテンツを各地に配って「高速化」
SSL通信の「暗号化」（鍵マーク）
セキュリティ（DDoS・WAF）サイトの「警備員」
Workers / Pagesエッジで動く「小さな実行環境・静的ホスティング」
今回使う用途: ① リバースプロキシ＝Origin Rules（/blog 振り分け・主目的）／② DNS（NS移管）／③ SSL（＋おまけでCDN高速化）。WAF・画像最適化・Workers有料等は使わない＝Freeで足りる。

なぜX-Serverではダメか

X-Serverとは役割が違う。X-Server＝中身の置き場（origin）／Cloudflare＝入口の前段（エッジ）。X-Serverに“交通整理”はできない。理由は3つ：

  1. 1
    DNSはホスト名単位。rincle.co.jp → どこか1つしか指せず、「/blogはこっち、それ以外はあっち」というパス単位の振り分けが原理的にできない
  2. 2
    共有レンタルサーバーなので、自分以外（Bubble）への自由なリバースプロキシ設定（mod_proxy等）が組めない
  3. 3
    仮にできても、全アクセスを共有サーバー経由でBubbleに中継＝遅い・不安定・本末転倒
ただしサブドメイン（blog.rincle.co.jp）ならX-Serverだけで完結（DNSにCNAMEを足してWordPressへ向けるだけ・Cloudflare不要）。その代わりSEOはサブディレクトリより弱い（＝方式B）。

ドメインサイトの住所の名前（rincle.co.jp）
