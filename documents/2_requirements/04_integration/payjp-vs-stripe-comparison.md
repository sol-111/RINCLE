# 決済基盤の方針 — Pay.jp vs Stripe 比較・移行計画（2026-06版）

> 初版: 2026/5/1 MTG を受けて比較資料として作成、5/8 定例で「Stripe推奨」を提示。
> **本版: 6/12 定例の再調査依頼（タスク#20）を受けて更新し、旧「Stripe移行方針」（4/21合意・stripe-migration-plan.md）を §9 に統合（2026-06-12）。**
> 再調査の前提: 「Pay.jpでオーソリを実装した上で、そのままPay.jpで行くか、Stripeに載せ替えるか」を**短期（工数）と中長期（メリット）の2軸**で評価する。

## 0. 結論サマリー

| 時間軸 | 結論 |
|--------|------|
| **短期**（決済失敗対策・キャンセルポリシー対応を最小工数で） | **Pay.jp続行が速い**。オーソリ実装は見積済み80h（2週間）で、載せ替え不要。ただしこの実装の一部（当日キャプチャ前提のバッチオーソリ）は、最終形が「予約時即時決済」なら将来捨てる |
| **中長期**（集約モデル・月額課金・3DS/CVC・全体実装） | **Stripe優位は維持**（Bubble公式プラグイン・3DS/CVCが素直・領収書/ApplePay等）。**ただし前回より差は縮んだ**: Pay.jpの3DSは対応済みと確認、手数料は新料金体系でPay.jpが安い（3.3% vs 3.6%、月商400万超なら2.78%） |
| **推奨ルート** | 増永さんの方針（急がない・二度手間回避・全体設計後にまとめて）に沿い、**決済全体の設計を固めてから、集約モデル実装のタイミングでStripeに載せ替えるのが引き続き合理的**。50円オーソリの先行実装（80h）は「夏シーズン中の保険」としてやるかどうかの経営判断 — 今の件数（月21件・失敗2件で原因特定済み）なら見送りに合理性あり |

## 1. 前提：新しい決済モデル（変更なし・4/21・5/1合意）

- **店頭決済（現金）を廃止**し、カード決済オンリーにする
- **PEDALSTANDARDが売上を一括回収**し、手数料を差し引いて店舗へ振込（6/12に「振り込まれる方が店舗のやってる感になる」+店舗月額課金構想で再確認）
- 店舗にPay.jp/Stripeのアカウントを作らせない（現行のPay.jpテナント型を廃止）
- 延長・店頭オプション・当日予約もシステム内のカード決済で完結（6/12）

```
エンドユーザー → 決済サービス → PEDALSTANDARDが一括受取
                                        ↓
                              手数料差引後、店舗へ振込
```

**背景（4/21合意時のPay.jpの課題・旧移行方針より）**: ①テナント型の制約で店舗ごとにPay.jpアカウント作成が必要（審査に数日・店舗の評判が悪い） ②手数料が「10%自動差引+5%紙請求」で煩雑 ③現行実装にセキュリティ問題（APIキー・顧客情報がDB上で閲覧可能）④カード登録時にCVC検証されない。

**重要な整理**: 「Pay.jp続行」もゼロ工数ではない。現行はPlatform API（テナント型・店舗へ自動分配・tenant/platform_fee必須）なので、集約モデルにするにはPay.jpでも単一アカウント型への作り替え+契約変更確認が必要。比較すべきは次の3ルート:

| ルート | 内容 | 位置づけ |
|--------|------|---------|
| A | 現行テナント型のまま**オーソリだけ先行実装** | 短期の保険（決済失敗・キャンセルポリシー対応） |
| B | **Pay.jpのまま集約モデル化**（単一アカウント型へ作り替え） | Pay.jp続行の本命形 |
| C | **Stripeへ載せ替え+集約モデル化** | 5/8時点の推奨 |

## 2. オーソリ仕様の比較（再調査の核心・2026-06確認）

| 項目 | Pay.jp（API v1・現行） | Pay.jp（API v2） | Stripe |
|------|----------------------|-----------------|--------|
| オーソリ有効期間 | **最大60日**（expiry_days=1〜60、デフォルト7日） | **最大30日** | 標準7日（Visa非対面は5日）だが、**日本アカウントの円建て取引は最長30日**（Visa/MC/JCB/Diners/Discover） |
| 海外発行カード | **2026年8月から最大7日に制限**（Pay.jp公式告知） | 同様 | ブランド標準（5〜7日）。日本特例30日が海外発行カードに及ぶかは要確認 |
| 部分キャプチャ（オーソリ金額以下） | ○ | ○ | ○（amount_to_capture指定・残額自動解放） |
| オーソリ金額超のキャプチャ | ×（エラー） | × | △（オーバーキャプチャは対象決済のみ） |
| 解放（キャンセル）手数料 | 無料 | 無料 | 無料 |
| 期限前の自動キャプチャ | ×（自前でバッチ管理） | × | ○（automatic_delayed・プレビュー機能） |

**含意:**
- RINCLEのユースケース（予約時50円検証→3日前全額オーソリ→当日キャプチャ / 貸出日のデポジットオーソリ数日間）は**どちらでも実現可能**。「Pay.jpは60日でStripeは7日だから長期予約はPay.jpしか無理」という前回の認識は、日本特例30日の確認により実質解消（30日超の先予約のみ要工夫 = 直前に再オーソリ or 50円検証のみ先行）
- 海外カード7日制限はPay.jpでも2026年8月から始まる。インバウンド対応を見据えるなら、どちらを選んでも「海外カードはオーソリ期間が短い」前提で設計が必要

出典: [Pay.jp オーソリと支払い確定](https://pay.jp/docs/authcapture) / [Pay.jp v2 仮売上ガイド](https://docs.pay.jp/v2/guide/status-management/auth-capture) / [海外発行カードのオーソリ期限制限（2026年8月〜）](https://pay.jp/info/2026-03-03-130000) / [Stripe: Place a hold](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)

## 3. 手数料比較（2026-06時点の公式料金で更新）

> 前回資料の「Pay.jp 3.0%/3.6%」は旧体系。現行プランは以下。

| 項目 | Pay.jp スタンダード | Pay.jp ビジネス | Stripe |
|------|--------------------|----------------|--------|
| 月額 | 0円 | 20,000円 | 0円 |
| 決済手数料 | **3.3%**（ブランド共通） | **2.78%**（月商400万〜2,000万向け） | **3.6%**（国内カード） |
| 返金手数料 | 無料 | 無料 | 無料（元の決済手数料は戻らない） |
| 振込手数料 | 250円/回 | 250円/回 | 無料 |

### 月間GMVごとの手数料負担シミュレーション

| 月間GMV | Pay.jp 3.3% | Pay.jp ビジネス（2.78%+2万） | Stripe 3.6% |
|---------|------------|------------------------------|-------------|
| 21.5万円（現在・2026-05実績） | 7,095円 | （対象外） | 7,740円 |
| 100万円 | 33,000円 | （損益分岐前） | 36,000円 |
| 400万円 | 132,000円 | 131,200円 | 144,000円 |
| 1,000万円 | 330,000円 | **298,000円** | 360,000円 |

**含意**: 現在の規模では月数百円の差で誤差。ただし**GMVがスケールするほどPay.jpのコスト優位が効いてくる**（月商1,000万で月6万円差）。前回「手数料はほぼ同等」とした判断は新料金体系では成り立たず、中長期の判断材料として復活。なお現行契約（テナント型・実効約3.5%店舗負担）から新料率への移行可否はPay.jpに要確認。

## 4. 3Dセキュア・CVC（前回から事実関係を更新）

| 項目 | Pay.jp | Stripe |
|------|--------|--------|
| EMV 3DS対応 | **○（対応済み）**。トークン作成時（カード登録時）/ 支払い時のどちらでも実施可。iframe型実装あり | ○（PaymentIntentで自動判定・標準対応） |
| 実装の手間（Bubble） | API Connector+リダイレクト/iframe組み込みを自前で（中規模） | プラグイン+PaymentIntentでほぼ自動（小） |
| カード登録時のCVC検証 | **×（仕様上、誤ったCVCでも登録できる）**= 5/15に確認した決済失敗の温床 | ○（登録時に検証） |

**重要**: EMV 3DSは**2025年3月末までにEC加盟店への導入が義務化済み**（クレカ・セキュリティガイドライン）。RINCLEは現在未導入のため、**どちらのサービスを選んでも3DS対応は必須タスク**であり「Stripeだから不要/Pay.jpだから不可」ではない。差は実装の手間（Stripeが軽い）と、CVC検証（Pay.jpは解決不可のまま）。未導入のまま運用を続けること自体がコンプライアンス・チャージバックリスクである点は増永さんに共有すべき。

出典: [PAY.JPにおける3Dセキュア](https://pay.jp/docs/guideline-payjp-three-d-secure) / [3DS組み込み方法の導入指針](https://pay.jp/docs/guideline-select-three-d-secure-type) / [EMV3DS導入義務化（Pay.jpヘルプ）](http://help.pay.jp/ja/articles/9555833-emv3d%E3%82%BB%E3%82%AD%E3%83%A5%E3%82%A2%E5%B0%8E%E5%85%A5%E7%BE%A9%E5%8B%99%E5%8C%96)

## 6. 短期工数の比較（オーソリ実装済み前提・3ルート）

### 共通タスク（どのルートでも必要）
全体の決済設計・キャンセルポリシー確定（#28）・**3DS対応（義務化済み）**・延長/オプション/当日決済のフロー・管理画面・振込オペ設計

### ルートA: 現行テナント型のまま オーソリだけ先行
| 項目 | 内容 |
|------|------|
| 工数 | **80h / 約2週間**（payjp-authorization-guide.md の見積・テスト込み） |
| 得られるもの | 50円カード検証→全額オーソリ→当日キャプチャ。決済失敗の事前検知・キャンセルポリシーの裏付け |
| 注意 | 集約モデルには未到達（紙請求・テナント分配が残る）。最終形が「予約時即時決済」なら**バッチオーソリ部分は捨てる**。3DSは含まれない |

### ルートB: Pay.jpのまま集約モデル化
| 項目 | 内容 |
|------|------|
| 主タスク | Platform API撤去・単一アカウント型へ作り替え（**契約変更の可否をPay.jpに要確認**）・3DS実装（中〜大）・予約時決済 or オーソリ流用 |
| 利点 | 顧客データ（cus_xxx）流用でカード再登録不要の可能性・手数料3.3%・ルートAの実装を一部流用できる |
| 弱点 | CVC未検証が残る・Bubbleプラグインなし・領収書/ApplePay等は自前 |

### ルートC: Stripeへ載せ替え+集約モデル化
| 項目 | 内容 |
|------|------|
| 主タスク | アカウント開設・公式プラグイン+PaymentIntent実装（3DS込み）・既存API定義撤去・**カード再登録（88人）**・オーソリはmanual captureで書き直し |
| 利点 | 3DS/CVC/領収書が一括解決・実装が素直・将来機能 |
| 弱点 | ルートAでオーソリを先行した場合、その80hの大半が二重作業になる（5/15で増永さんも認識済み） |

**短期の結論**: 「今すぐ決済失敗対策をしたい」ならルートA一択（80h）。ただし6/12に「今の件数なら急がない」で合意済みなので、**ルートAをスキップして全体設計→B or C に直行するのが二度手間最小**。BとC単体の工数は前回調査どおり「ほぼ同等」（共通タスクが大半。Cはカード再登録が増え、Bは3DS実装と契約変更リスクが増える）。

## 7. 「Pay.jpオーソリ80h」は将来資産になるか（6/12の論点）

| 実装要素 | 最終形（予約時即時決済・集約）での扱い |
|----------|--------------------------------------|
| 予約時50円オーソリ（カード有効性チェック） | **生き残る**（キャンセルポリシー・当日予約の与信に最終形でも使う） |
| 3日前バッチオーソリ→当日キャプチャ | **捨てる可能性が高い**（予約時即時決済なら不要） |
| デポジットオーソリ（貸出日・数日間） | 生き残る（ただし増永さんは導入自体に消極的寄り・#25調査待ち） |
| 実装ノウハウ（charge_id管理・テストケース） | 設計としては流用可。ただしコードはサービス固有なのでStripe移行時は書き直し |

→ ルートA(80h)のうち、純粋な掛け捨てになるのは概ね半分（バッチオーソリ+Pay.jp固有実装）。「夏の繁忙期に決済失敗ゼロで走りたい」なら保険料として成立するが、急がないなら払う必要のないコスト。

## 9. 決定後の移行計画（旧「Stripe移行方針」を統合・2026-06更新）

> 4/21・5/1合意の実行計画。Stripeを選んだ場合のフロー設計と移行ステップ。Pay.jp集約化（ルートB）でも決済フローの構造は同じ（PaymentIntent→PaymentFlow/Chargeに読み替え）。

### 9.1 決済フロー設計

| シーン | フロー | 要点 |
|--------|--------|------|
| 予約時決済 | 予約+カード入力 → PaymentIntent即時決済 → 予約確定・在庫確保 | 全額即時決済（オーソリではない）。現金廃止・カードオンリー。3DSは自動 |
| キャンセル | キャンセル操作 → Refund（全額 or 一部） → 在庫開放 | 即時決済のため**返金**で処理。キャンセルポリシー（#28）が前提 |
| 延長 | 店舗が延長操作 → 登録済みカードで追加PaymentIntent | 元の予約とは別決済。予約IDとの紐付けをDBで管理（延長手数料の取りこぼし#19も解消） |
| 店頭オプション | 店舗が選択 → 登録済みカードで追加決済 | 現在システム外の売上を捕捉できるようになる |
| 高級車デポジット | 通常料金は即時決済 + 貸出日にデポジット分をオーソリ（capture_method=manual・数日間） | 返却時に問題なければ解放・損傷等あればキャプチャ。導入自体は#25の与信調査待ち |

### 9.2 店舗への振込・登録

- **振込**: 月次で店舗別売上を集計 → カード手数料+利用料15%を差引 → 振込。紙請求は廃止、未払いリスクゼロ
- **店舗登録**: 決済アカウント作成・審査（現行8ステップ）が丸ごと不要に。店舗情報の代行入力運用は継続
- **領収書**: お金の当事者がユーザー⇔PEDALSTANDARDになるため発行元が変わる見込み。Stripeのレシートメール自動送信を利用（法的要件は要確認）

### 9.3 移行ステップ（2026-06時点のステータス）

| Phase | 内容 | 状態 |
|-------|------|------|
| 0: 現行の緊急修正 | 手数料10%→15%（済）/ 延長決済の処理不備・カード選択不具合・DBセキュリティ | **15%は完了**。残りは**DB再構築（#4・〜6月末）に統合済み** |
| 1: 方針確定・設計 | 決済サービス最終決定（#20）/ 弁護士回答 / キャンセルポリシー確定（#28）/ 詳細設計 | **いまここ**。#20・#25の調査結果と合わせて次回以降の定例で決定 |
| 2: 実装 | 予約時決済・返金・延長/オプション決済・管理画面・（デポジット） | DB再構築完了後。全体設計を固めてからまとめて実装（6/12合意・二度手間回避） |
| 3: 切替 | E2E検証 / カード再登録案内（88人） / 本番切替 / Pay.jpテナント廃止 / 振込運用開始 | Phase 2の後 |
