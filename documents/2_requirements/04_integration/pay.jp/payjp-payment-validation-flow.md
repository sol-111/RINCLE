# 決済失敗防止フロー（3段階バリデーション）

> 事前予約（最大60日前）でも決済失敗を防ぐための段階的バリデーション設計。
> `payjp-flow-tobe.md` の予約〜キャプチャフローを補完する。

---

## 用語整理

PAY.JPの用語は紛らわしいので先に整理する。

`capture` は「捕まえる・確定する」という意味。
- `capture: false` → 確定**しない**（枠だけ押さえる）
- `capture: true` → 確定**する**（引き落とす）

`capture: false` は「検証に失敗した」ではなく「**あえて確定させない**」という指示。

| 用語 | 意味 | お金動く？ |
|---|---|---|
| オーソリ（`capture: false`） | 与信枠を押さえるだけ | 動かない |
| キャプチャ（`capture: true`） | 押さえた枠を確定して引き落とす | 動く |
| refund | オーソリ解放 or 返金 | 戻す |

---

## 背景・課題

- PAY.JPではCVCチェックはカード情報のトークン化時にしか行えない（PCI-DSSによりCVCの保存が禁止されているため）
- 現行フロー（To-Be）では、予約時にオーソリ → 当日キャプチャだが、**30日以上前の予約ではイシュア側のオーソリ保持期間が切れるリスク**がある
- customerに保存済みのカードへの課金ではCVCが再送されないため、**カード登録時にCVC検証を確実に行う必要がある**

### なぜ予約時（60日前）にオーソリしないのか

PAY.JPの `expiry_days=60` とイシュア（カード発行会社）側のオーソリ保持期間は**別物**。

| | 期間 |
|---|---|
| PAY.JPのキャプチャ期限（`expiry_days`） | 最大60日（PAY.JPのシステム上の期限） |
| イシュア側のオーソリ保持期間 | **一般的に7〜30日**（イシュアが独自に管理） |

PAY.JP上でキャプチャ可能でも、イシュアが与信枠を解放済みだとキャプチャが失敗する。
また、60日の間にカード停止・残高不足・限度額超過が発生する可能性もある。

そのため、**予約日の3日前にオーソリを実施**することで：
- イシュアの保持期間内に確実にキャプチャできる
- カードの**最新の状態**でチェックできる

## 3段階バリデーション

```
予約時（カード登録）
  ├─ Checkout.js → トークン作成
  ├─ トークンで¥50オーソリ（capture: false）← CVCチェックはここだけ
  ├─ 成功 → 即refund + customerに保存
  └─ 失敗 → エラー表示、予約させない

2〜3日前（バッチ）
  ├─ customer IDで本番金額オーソリ（capture: false）← カード有効・残高チェック
  ├─ 成功 → charge_id保存
  └─ 失敗 → メール通知「カード更新してください」

当日（ライド開始）
  └─ charge_idをキャプチャ（capture）
```

### STEP 1とSTEP 2の違い

どちらも `capture: false`（オーソリ）だが、使用するキーが異なる。

| | STEP 1（予約時） | STEP 2（3日前） |
|---|---|---|
| 使用するキー | **トークン**（`tok_xxx`） | **customer ID**（`cus_xxx`） |
| CVCの情報 | トークンに含まれている | **なし**（PCI-DSSにより保存禁止） |
| CVCチェック | **される** | されない |
| 目的 | CVC検証 | カード有効・残高確認 |

- トークンはCheckout.js（カード入力フォーム）で作成された直後のみ使用可能で、CVCの情報が含まれている
- カードをcustomerとして保存した時点でCVCは破棄されるため、以降customer IDでの課金ではCVCは二度とチェックされない
- **CVCチェックはSTEP 1でしか実施できない**

### 各ステップで潰せるリスク

| ステップ | 潰せるリスク |
|---|---|
| 予約時¥50オーソリ | CVC不一致、無効カード、有効期限切れ |
| 2〜3日前オーソリ | カード停止、残高不足、限度額超過 |
| 当日キャプチャ | 与信確保済みなのでほぼ失敗しない |

---

## STEP 1: 予約時（カード登録 + CVC検証）

### 目的

カードの有効性とCVCをイシュアに照合し、不正カード・無効カードを予約段階で弾く。

### 処理フロー

```
① エンドユーザー: Checkout.jsでカード情報入力（番号・有効期限・CVC）
      ↓
② Checkout.js → PAY.jp: トークン作成
   ※ この時点ではフォーマットチェックのみ。イシュアへのCVC照合はまだ行われない
      ↓
③ RINCLE → PAY.jp: トークンで¥50オーソリ（capture: false）
   POST /v1/charges
   {
     "amount": 50,
     "currency": "jpy",
     "card": "tok_xxxx",    ← トークンを直接使う（customerではない）
     "capture": false,
     "expiry_days": 1
   }
   ※ トークンにCVC情報が含まれているため、イシュアがCVCを照合する
      ↓
④ 【成功の場合】
   RINCLE → PAY.jp: 即refund（与信解放）
   POST /v1/charges/{charge_id}/refund
      ↓
⑤ RINCLE → PAY.jp: カードをcustomerに保存
   POST /v1/customers/{customer_id}
   ※ 以降の課金はcustomer IDで行う（CVCは保存されない）
      ↓
⑥ RINCLE: 予約確定・在庫確保

④' 【失敗の場合】
   → エラー表示「カード情報をご確認ください」
   → 別カードでの再試行を促す
   → 予約は確定させない
```

### ポイント

- **¥50はPAY.JPの最低課金額**（¥0オーソリは不可）
- **トークンを直接使う**ことでCVCがイシュアに送信される。customer経由だとCVCは送れない
- refund後、エンドユーザーの明細には何も残らない（引き落としていないため）
- `expiry_days: 1` で即失効させる（長期保持する意味がないため）

## STEP 2: 2〜3日前（バッチオーソリ）

### 目的

予約日直前にカードの現在の状態を確認し、本番金額の与信枠を確保する。

### 処理フロー

```
① Bubbleの定期ワークフロー（Recurring Workflow）: 毎日AM9:00に実行
      ↓
② 検索条件:
   - 予約日が2〜3日後
   - 支払方法が「クレジット」
   - charge_idが空（まだオーソリしていない）
      ↓
③ 各予約に対して:
   RINCLE → PAY.jp: 本番金額でオーソリ（capture: false）
   POST /v1/charges
   {
     "customer": "cus_xxxx",   ← 保存済みcustomer
     "amount": <予約金額>,
     "currency": "jpy",
     "capture": false,
     "tenant": "ten_xxxx",
     "expiry_days": 7
   }
      ↓
④ 【成功の場合】
   → charge_idを予約レコードに保存
   → ステータスを「決済準備完了」に更新
      ↓
④' 【失敗の場合】
   → エンドユーザーにメール通知
     「ご予約の決済処理に失敗しました。カード情報をご確認ください」
   → RINCLE管理者にも通知（Slack or メール）
   → ステータスを「要カード更新」に更新
```

### 失敗時のリカバリフロー

```
オーソリ失敗
  ↓
メール通知（即時）: 「カード情報を更新してください」
  ↓
24時間後リマインド: 「まだカード情報が更新されていません」
  ↓
前日まで更新なし:
  ├─ 選択肢A: 予約を自動キャンセル
  └─ 選択肢B: 現地払いに切替（店舗に通知）
  ※ どちらを採用するかは要決定
```

### ポイント

- **customer IDでの課金のためCVC再チェックはされない**（STEP 1で検証済み）
- `expiry_days: 7` で余裕を持たせる（予約日の2〜3日前に実行するため）
- バッチ実行タイミングは予約日の**3日前**が推奨（リカバリの時間を確保するため）

---

## STEP 3: 当日（キャプチャ）

### 目的

STEP 2で確保した与信枠を確定し、実際に課金する。

### 処理フロー

```
① 加盟店: 店舗管理画面で「ライド開始」をクリック
      ↓
② RINCLE → PAY.jp: キャプチャ
   POST /v1/charges/{charge_id}/capture
      ↓
③ 【成功の場合】
   → ステータスを「ライド中」に更新
   → 加盟店: バイク貸出
      ↓
③' 【キャプチャ失敗の場合】（まれ）
   → 別カードで再決済 or 現地払いへ切替
```

### ポイント

- STEP 2でオーソリ済みのため、**キャプチャ失敗はほぼ発生しない**
- 万が一失敗する場合: オーソリ後にカードが停止された等の極めてまれなケース
- `payjp-flow-tobe.md` のキャプチャフロー（セクション3）と同じ処理

---

## 予約日までの日数による分岐

予約日が近い場合はSTEP 2をスキップできる。

| 予約〜利用日 | STEP 1（予約時） | STEP 2（バッチ） | STEP 3（当日） |
|---|---|---|---|
| 当日〜3日以内 | **本番金額でオーソリ**（¥50スキップ） | スキップ | キャプチャ |
| 4日〜60日 | ¥50オーソリのみ | 本番金額オーソリ | キャプチャ |

- 3日以内の予約は、¥50オーソリをスキップし、**トークンで直接本番金額のオーソリを実行**する（CVCチェック + 与信確保を1回で済ませる）
- トークンは1回しか使えないため、¥50オーソリと本番金額オーソリを同じトークンで2回行うことはできない
- 4日以上先の予約は、¥50オーソリ（CVCチェック）のみ行い、バッチで後日本番金額オーソリする

### 60日前予約の具体例

```
60日前に予約
  ├─ STEP 1: ¥50オーソリ+即refund（CVCチェック）← この日
  │
  │  ... 57日間は何もしない ...
  │
  ├─ STEP 2: 本番金額オーソリ（3日前）← expiry_days=7 で十分
  │
  └─ STEP 3: キャプチャ（当日）← オーソリから3日以内なので余裕
```

STEP 2のオーソリは予約日の3日前に行うため、オーソリ保持期間（60日）の問題は発生しない。
60日前だろうが当日だろうが同じフローで処理できる。

## Bubble実装メモ

### 必要なAPI Connector追加・変更

| 用途 | メソッド | エンドポイント | 備考 |
|---|---|---|---|
| ¥50オーソリ（トークン直接） | POST | `/v1/charges` | `card`パラメータにトークンを渡す（既存のCharge_by_car_idとは別） |
| オーソリrefund | POST | `/v1/charges/{id}/refund` | 既存のCharge_refundを流用可 |
| バッチオーソリ | POST | `/v1/charges` | 既存のCharge_by_car_idに`capture=false`を追加 |
| キャプチャ | POST | `/v1/charges/{id}/capture` | 新規追加 |

### 予約情報テーブルへの追加フィールド

| フィールド | 型 | 用途 |
|---|---|---|
| `cvc_check_charge_id` | text | STEP 1の¥50オーソリのcharge_id（refund用） |
| `auth_charge_id` | text | STEP 2の本番オーソリのcharge_id（キャプチャ用） |
| `auth_status` | text | `pending` / `authorized` / `failed` / `captured` |
| `auth_failed_at` | date | オーソリ失敗日時（リマインド送信の起算点） |

### Recurring Workflow設定

- **スケジュール**: 毎日AM9:00
- **対象**: 予約日が3日後 & 支払方法=クレジット & auth_status=pending
- **処理**: オーソリ実行 → 結果に応じてauth_status更新 + 通知
