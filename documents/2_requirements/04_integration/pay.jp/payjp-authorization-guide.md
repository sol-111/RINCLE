## 1. そもそもオーソリとは？

### 一言で言うと

**「お金を引き落とさずに、カードの与信枠だけ確保すること」**

### 身近な例

ホテルの予約を思い出してください。

```
チェックイン時:
  ホテル「カードを確認させてください」
  → カードの枠だけ押さえる（引き落としはしない）  ← これがオーソリ

チェックアウト時:
  ホテル「宿泊料を確定します」
  → 実際にお金を引き落とす                        ← これがキャプチャ

キャンセル時:
  ホテル「予約をキャンセルしました」
  → 押さえていた枠を解放する（返金処理は不要）     ← オーソリ解放
```

### Pay.JP API での対応

| 概念 | Pay.JP API | パラメータ |
|------|-----------|-----------|
| **オーソリ**（与信確保） | `POST /v1/charges` | `capture=false` |
| **キャプチャ**（売上確定） | `POST /v1/charges/{id}/capture` | - |
| **即時課金**（現行方式） | `POST /v1/charges` | `capture=true`（デフォルト） |

### なぜオーソリが必要？

```
【現行の問題】
  予約確定 ─── （数日〜数週間） ──→ ライド当日に課金
                                      ↑
                                    この時にカードが使えないと
                                    お金を回収できない！（未回収リスク）

【オーソリを入れると】
  予約確定時にオーソリ ──→ カード枠を確保済み ──→ ライド当日にキャプチャ
  （お金は取らない）        （安心）                （確実に回収）
```

## 2. 現行の決済フロー（問題点）

### 現行フロー図

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│  予約確定時   │    │  ライド開始時  │    │  キャンセル時  │
│              │    │              │    │              │
│ カード登録のみ │──→│ 直接課金      │    │ 返金処理      │
│ (課金なし)    │    │ capture=true  │    │ /refund       │
│              │    │              │    │              │
│ ⚠ 枠確保なし │    │ ⚠ 失敗リスク  │    │ ⚠ 手間がかかる│
└─────────────┘    └──────────────┘    └──────────────┘
```

### 何が問題？

| # | 問題 | 影響 |
|---|------|------|
| 1 | 予約時にカード枠を確保していない | ライド当日にカードが使えなくなっている可能性がある |
| 2 | キャンセル時に「返金」処理が必要 | まだお金を取っていないのに返金するのは無駄な手順 |
| 3 | 返金処理は手数料が発生する場合がある | コスト増 |

## 3. オーソリを使った新しい決済フロー

### 新フロー図

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  予約確定時    │    │  ライド開始時  │    │  キャンセル時  │
│              │    │              │    │              │
│ オーソリ      │──→│ キャプチャ     │    │ 何もしない    │
│ capture=false │    │ /capture      │    │ (自動解放)    │
│              │    │              │    │              │
│ ✅ 枠確保済み │    │ ✅ 確実に回収  │    │ ✅ 手間ゼロ   │
└──────────────┘    └──────────────┘    └──────────────┘
```

### 各ステップのAPI呼び出し

#### Step 1: 予約時 — オーソリ（与信確保）

```
POST https://api.pay.jp/v1/charges

パラメータ:
  customer:     cus_xxxxx        ← 顧客ID
  amount:       10000            ← 金額（円）
  currency:     jpy
  capture:      false            ← ★ これがオーソリのキモ！
  expiry_days:  60               ← ★ 与信枠の有効期限（最大60日）
  tenant:       ten_xxxxx        ← 店舗テナントID
  platform_fee: 1000             ← プラットフォーム手数料

レスポンス:
  {
    "id": "ch_xxxxx",            ← このIDを必ず保存する！
    "captured": false,           ← falseならオーソリ状態
    "amount": 10000,
    "expiry_days": 60
  }
```

#### Step 2: ライド開始時 — キャプチャ（売上確定）

```
POST https://api.pay.jp/v1/charges/{charge_id}/capture

パラメータ: なし（オーソリ時の金額で確定）
  ※ 金額を変更したい場合は amount パラメータを指定可能

レスポンス:
  {
    "id": "ch_xxxxx",
    "captured": true,            ← trueに変わる = 課金確定
    "amount": 10000
  }
```

#### Step 3: キャンセル時 — オーソリ解放

```
特別なAPI呼び出しは不要！

→ expiry_days で指定した期間が過ぎると自動的に解放される
→ または、Charge を refund すると即座に解放される
  （オーソリ状態の refund = 枠の解放。返金ではない）
```

## 4. 実装手順（ステップバイステップ）

### 前提: 現行のBubble API Connector設定

現在、以下のAPIコネクタが設定済み:

| Bubble WF ID | 名前 | 用途 |
|---|---|---|
| `bTVIE` | `Charge_by_car_id` | 課金実行（`capture=true` 固定） |
| `bTVFu` | `Charge_refund` | 返金 |

### 手順 1: API Connector に「キャプチャ用API」を追加

> **なぜ必要？** 現在 `/charges/{id}/capture` のAPIコネクタが存在しない。

1. Bubble エディタ → Plugins → API Connector を開く
2. Pay.JP API (`bTHZi`) の中に新しい API Call を追加
3. 以下の設定を入力:

```
Name:           Charge_capture
Method:         POST
URL:            https://api.pay.jp/v1/charges/[charge_id]/capture
Authentication: Basic (Secret Key をユーザー名に設定)

URL Parameters:
  - charge_id (text, required)     ← URLパスに埋め込む

Body Parameters:
  - amount (number, optional)      ← 金額変更時のみ指定

Response:
  - id (text)
  - captured (boolean)
  - amount (number)
```

**設定画面イメージ:**

```
┌─────────────────────────────────────────────┐
│ API Call: Charge_capture                     │
│                                             │
│ Method: [POST ▼]                            │
│                                             │
│ URL: https://api.pay.jp/v1/charges/         │
│      [charge_id]/capture                    │
│                                             │
│ Authentication:                             │
│   Type: [HTTP Basic Auth ▼]                 │
│   Username: sk_test_xxxx  ← Secret Key      │
│   Password: (空欄)                           │
│                                             │
│ Body type: [Form-data ▼]                    │
│                                             │
│ Parameters:                                 │
│   charge_id  [text]   [required] [in URL]   │
│   amount     [number] [optional] [in body]  │
└─────────────────────────────────────────────┘
```

### 手順 2: 既存の `Charge_by_car_id` を修正

> **何を変える？** `capture` パラメータを追加して、オーソリ/即時課金を切り替え可能にする。

1. `Charge_by_car_id` (`bTVIE`) を開く
2. Body Parameters に以下を追加:

```
追加パラメータ:
  - capture      (boolean, optional)    ← false=オーソリ, true=即時課金
  - expiry_days  (number, optional)     ← オーソリの有効期限（日数、最大60）
```

**既存パラメータ（変更なし）:**

```
  - customer     (text, required)       ← 顧客ID
  - amount       (number, required)     ← 金額
  - currency     (text, required)       ← "jpy"
  - tenant       (text, required)       ← テナントID
  - platform_fee (number, required)     ← プラットフォーム手数料
```

### 手順 3: 予約ワークフローの修正

> **場所:** 予約確定ボタンのワークフロー

**変更前（現行）:**
```
予約確定ボタン クリック時:
  1. 予約データを作成
  2. 在庫を確保
  3. (課金なし — ライド開始まで待つ)
```

**変更後（オーソリ追加）:**
```
予約確定ボタン クリック時:
  1. 予約データを作成
  2. 在庫を確保
  3. ★ Pay.JP API → Charge_by_car_id を実行
     - customer:     Current User の cus_id
     - amount:       予約金額
     - currency:     "jpy"
     - tenant:       店舗の tenant_id
     - platform_fee: 予約金額 × 10%
     - capture:      false               ← ★ オーソリ！
     - expiry_days:  60                   ← ★ 有効期限60日
  4. ★ 予約データの charge_id に レスポンスの id を保存
  5. ★ 予約データの payment_status を "authorized" に更新
```

**超重要: charge_id を必ず保存すること！**
→ 保存しないとキャプチャ時に charge_id がわからず、課金確定ができない。

### 手順 4: ライド開始ワークフローの修正

> **場所:** shop_admin の「ライド開始」ボタンのワークフロー

**変更前（現行）:**
```
ライド開始ボタン クリック時:
  1. Pay.JP API → Charge_by_car_id を実行（即時課金）
  2. charge_id を保存
  3. ステータスを更新
```

**変更後（キャプチャに変更）:**
```
ライド開始ボタン クリック時:
  1. ★ Pay.JP API → Charge_capture を実行
     - charge_id: 予約データの charge_id    ← オーソリ時に保存したID
  2. ★ 予約データの payment_status を "captured" に更新
  3. ステータスを更新
```

### 手順 5: キャンセルワークフローの修正

> **場所:** キャンセルボタンのワークフロー

**変更前（現行）:**
```
キャンセルボタン クリック時:
  1. Pay.JP API → Charge_refund を実行（返金）
  2. ステータスをキャンセルに更新
```

**変更後（オーソリ解放に変更）:**
```
キャンセルボタン クリック時:
  1. 条件分岐:

     【payment_status が "authorized" の場合】（オーソリ状態 = まだお金を取っていない）
       → Pay.JP API → Charge_refund を実行
         ※ オーソリ状態での refund = 枠の解放（返金ではない）
       → payment_status を "cancelled" に更新

     【payment_status が "captured" の場合】（キャプチャ済み = お金を取った後）
       → Pay.JP API → Charge_refund を実行（実際の返金）
       → payment_status を "refunded" に更新

  2. 予約ステータスをキャンセルに更新
```

### 手順 6: DBフィールドの追加

> **テーブル:** 予約（Reservation）

| フィールド名 | 型 | 説明 |
|---|---|---|
| `payment_status` | text | 決済状態（"authorized" / "captured" / "cancelled" / "refunded"） |

**既存フィールド（変更不要）:**

| フィールド名 | 型 | 説明 |
|---|---|---|
| `charge_id` | text | チャージID（オーソリ時に保存） |
| `__charge_id` | text | 延長料金のチャージID |

## 5. はまりポイント集（よくあるミス）

### はまりポイント 1: `capture=false` の指定忘れ

```
❌ ダメな例:
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  currency: jpy
  ← capture パラメータなし（デフォルト true = 即時課金！）

✅ 正しい例:
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  currency: jpy
  capture: false        ← これを必ず指定！
```

**被害:** お客さんの予約確定時に即座にお金が引き落とされる。
**対策:** Bubble のワークフローで `capture` フィールドに `false` をハードコーディングし、条件分岐ではなく常にオーソリとする。

---

### はまりポイント 2: charge_id の保存忘れ

```
❌ ダメな例:
  オーソリ実行 → レスポンス受け取る → charge_id を保存しない
  ↓
  キャプチャ時: charge_id がないのでキャプチャできない！！

✅ 正しい例:
  オーソリ実行 → レスポンスの id を予約の charge_id フィールドに即座に保存
```

**被害:** キャプチャ不可 = お金を回収できない。最悪のシナリオ。
**対策:** オーソリ API 呼び出しの直後のステップで、必ず charge_id を保存する。

> **実際にこのバグが起きている！**
> 現行システムの延長決済で `__charge_id` の保存漏れが発生中。延長分の返金ができない状態。
> 同じミスを絶対に繰り返さないこと。

---

### はまりポイント 3: `expiry_days` の上限は60日

```
❌ ダメな例:
  expiry_days: 90    ← エラーにはならないが、60日を超える値は無視される

✅ 正しい例:
  expiry_days: 60    ← 最大60日
```

**被害:** 予約日がオーソリから60日以上先だと、ライド当日にキャプチャしようとしても失効済み。
**対策:**
- 営業カレンダーの予約可能範囲を60日以内に制限する
- 予約日までの日数が60日を超える場合、予約直前（60日以内）にオーソリを実行するバッチ処理を組む

```
【具体的な計算例】
  今日: 2026-05-15
  予約日: 2026-07-20（66日後）

  → 60日を超えている！
  → 対策A: 予約不可にする
  → 対策B: 2026-05-21（予約日の60日前）にオーソリを実行するスケジュールを設定
```

---

### はまりポイント 4: 海外カードのオーソリ有効期限は7日！

```
日本発行カード: expiry_days 最大60日
海外発行カード: expiry_days 最大 7日 ← ★ 要注意！
```

**被害:** 海外のお客さんの予約で、7日以上先の予約だとキャプチャ時に失効。
**確認方法:** テストカード `4000000900000003`（`is_jp=false`）で検証可能。
**対策:**
- 海外カード判定が難しい場合は、予約可能範囲を7日以内にするか
- キャプチャ失敗時に再オーソリ → キャプチャのリトライフローを組む

---

### はまりポイント 5: キャプチャ時の金額変更に要注意

```
オーソリ時:   amount = 10,000円
キャプチャ時: amount = 12,000円  ← オーソリ時の金額を超えた！

→ エラーになる！（超過分のキャプチャは不可）
```

**ルール:**
- キャプチャ時の金額 ≦ オーソリ時の金額 → OK
- キャプチャ時の金額 > オーソリ時の金額 → NG（エラー）

**被害:** 延長料金などで追加が発生した場合、キャプチャ金額がオーソリ金額を超えてエラー。
**対策:**
- 延長分は**別のチャージ**として新規に課金する（現行と同じ `Charge_by_car_id` で `capture=true`）
- オーソリ時に多めの金額で確保しておく（ただしユーザーのカード枠を圧迫するので非推奨）

```
【推奨パターン】
  予約時:     オーソリ 10,000円（charge_id = ch_001）
  ライド開始: キャプチャ 10,000円（ch_001 をキャプチャ）
  延長発生:   新規課金  3,000円（capture=true で別チャージ ch_002 を作成）
```

### はまりポイント 6: テスト環境で本番キーを使わない

```
❌ ダメな例:
  テスト時に sk_live_xxxx を使う
  → テストカード（4242424242424242）が使えない！
  → 本物のカードで本物の課金が走る！

✅ 正しい例:
  テスト時は sk_test_xxxx / pk_test_xxxx を使う
  → テストカードが使える
  → 本物の課金は発生しない
```

**被害:** 本番データ汚染、実課金発生。
**対策:** API Connector の Secret Key が `sk_test_` で始まっていることを必ず確認。

> **実際にこの問題が起きている！**
> 現行システムで本番キーが開発環境に設定されている。Issue #3 で対応中。

---

### はまりポイント 7: オーソリ失効後のキャプチャ

```
❌ ダメな例:
  5月1日: オーソリ（expiry_days=60）
  7月5日: キャプチャ（65日後）
  → エラー! "This charge has already expired" 的なエラー

✅ 正しい例:
  5月1日: オーソリ（expiry_days=60）
  6月25日: キャプチャ（55日後）
  → 成功
```

**対策:**
- キャプチャ前に charge の状態を `GET /v1/charges/{id}` で確認する
- `expired_at` フィールドで失効日時をチェック
- 失効していたら、再度オーソリを取り直す

```
【安全なキャプチャフロー】
  1. GET /v1/charges/{charge_id} で状態確認
  2. captured=false かつ 失効していない → キャプチャ実行
  3. 失効済み → 再オーソリ → 成功したらキャプチャ
  4. 再オーソリも失敗 → 管理者に通知（カードが使えなくなった可能性）
```

### はまりポイント 8: 二重キャプチャ

```
❌ ダメな例:
  1回目: POST /charges/ch_xxx/capture → 成功
  2回目: POST /charges/ch_xxx/capture → エラー!
  "This charge has already been captured"

✅ 正しい例:
  キャプチャ前に captured 状態を確認してから実行
```

**被害:** エラーが発生してユーザーに不要なエラーメッセージが表示される。
**対策:**
- キャプチャ前に `payment_status` を確認し、`"authorized"` の場合のみキャプチャを実行
- ボタンの連打防止（Bubble の "This element isn't clickable" 条件を設定）

---

### はまりポイント 9: Platform API での tenant 指定忘れ

```
❌ ダメな例:
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  capture: false
  ← tenant がない！

→ エラー: "tenant is required for platform charges"

✅ 正しい例:
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  capture: false
  tenant: ten_xxxxx        ← 必須！
  platform_fee: 1000       ← 必須！
```

**被害:** オーソリ自体が失敗する。
**対策:** RINCLE は Marketplace型の Platform API を使っているため、`tenant` と `platform_fee` は常に必須。

---

### はまりポイント 10: Webhook の `charge.captured` イベント

```
キャプチャ成功時:
  Pay.JP → Webhook → charge.captured イベントを送信
  → Rincle の Webhook ハンドラで受信

注意:
  即時課金（capture=true）でも charge.captured は発火する
  オーソリ→キャプチャ でも charge.captured は発火する

  → Webhook 側で「オーソリからのキャプチャ」と「即時課金」を
    区別する必要がある場合は、独自の payment_status で管理すること
```

## 6. テスト手順

### Step 1: テスト環境の確認

```
1. Bubble エディタ → Plugins → API Connector → Pay.JP API
2. Secret Key が sk_test_xxxx で始まっていることを確認
3. ページの Checkout.js が pk_test_xxxx を使っていることを確認
```

### Step 2: テストカード一覧

#### 正常系（成功するカード）

| カード番号 | ブランド | 用途 |
|-----------|---------|------|
| `4242 4242 4242 4242` | Visa | **基本テストに使用** |
| `5555 5555 5555 4444` | Mastercard | ブランド別テスト |
| `3530 1113 3330 0000` | JCB | ブランド別テスト |

- 有効期限: 未来の任意の年月（例: `12/30`）
- CVC: 任意の3桁（例: `123`）

#### 異常系（エラーを再現するカード）

| カード番号 | エラー | テスト内容 |
|-----------|--------|----------|
| `4000 0000 0000 0002` | `card_declined` | カード利用不可 |
| `4000 0000 0008 0319` | `card_declined`（Charge時） | **トークンは成功、課金時にエラー** |
| `4000 0000 0008 0202` | `card_declined` | 10,000円超で与信枠超過 |
| `4000 0009 0000 0003` | 海外カード | **オーソリ有効期限が7日に制限** |

### Step 3: テストシナリオ

#### シナリオ A: 正常フロー（オーソリ → キャプチャ）

```
1. テストカード 4242424242424242 でカード登録
2. 予約を作成
3. 予約確定 → オーソリが実行されることを確認
   確認ポイント:
   - charge_id が予約に保存されている
   - payment_status が "authorized"
   - Pay.JP 管理画面で該当 charge の captured が false
4. ライド開始 → キャプチャが実行されることを確認
   確認ポイント:
   - payment_status が "captured" に変わる
   - Pay.JP 管理画面で captured が true
```

#### シナリオ B: キャンセルフロー（オーソリ → 解放）

```
1. テストカード 4242424242424242 でカード登録
2. 予約を作成・確定（オーソリ実行）
3. 予約をキャンセル
   確認ポイント:
   - 返金処理ではなくオーソリ解放が実行される
   - payment_status が "cancelled"
   - Pay.JP 管理画面で refunded が true（オーソリ解放）
```

#### シナリオ C: カードエラーフロー

```
1. テストカード 4000000000080319 でカード登録
   → カード登録自体は成功する
2. 予約を作成・確定 → オーソリ実行
   → card_declined エラーが発生する
   確認ポイント:
   - エラーがユーザーに分かりやすく表示される
   - 予約がキャンセルまたは保留状態になる
   - charge_id は保存されない（オーソリ失敗のため）
```

#### シナリオ D: 延長決済フロー

```
1. 正常フローでオーソリ → キャプチャまで完了
2. 延長操作を実行
   確認ポイント:
   - 延長分は別の charge_id で新規課金される
   - __charge_id フィールドに延長分の charge_id が保存される
   - 延長分の返金が可能であることを確認
```

### Step 4: Pay.JP 管理画面での確認方法

```
1. https://pay.jp にログイン
2. 左メニュー「売上」→「支払い」を選択
3. テストモードになっていることを確認（画面上部にテストモード表示）
4. 対象の charge_id を検索
5. 以下を確認:
   - captured: false（オーソリ状態） / true（キャプチャ済み）
   - amount: 金額
   - tenant: テナントID
   - refunded: 返金/解放済みかどうか
```

## 7. エラーコード一覧と対処法

### オーソリ時に発生しうるエラー

| エラーコード | 意味 | ユーザーへの表示例 | 対処法 |
|---|---|---|---|
| `card_declined` | カード利用不可 | 「このカードはご利用いただけません。別のカードをお試しください」 | 別カードを登録してもらう |
| `expired_card` | 有効期限切れ | 「カードの有効期限が切れています。新しいカードを登録してください」 | カード再登録 |
| `insufficient_fund` | 与信枠不足 | 「カードの利用限度額を超えています」 | 別カードまたはカード会社に連絡 |
| `processing_error` | Pay.JP側エラー | 「一時的なエラーが発生しました。しばらくしてからお試しください」 | リトライ |

### キャプチャ時に発生しうるエラー

| エラーコード | 意味 | 対処法 |
|---|---|---|
| `already_captured` | 二重キャプチャ | payment_status を確認、すでに captured なら何もしない |
| `charge_expired` | オーソリ失効 | 再オーソリを取り直す → 成功したらキャプチャ |
| `invalid_amount` | 金額超過 | オーソリ時の金額以下でキャプチャする |

### リスク要因（工数が伸びる可能性があるもの）

| リスク | 影響 | 発生確率 |
|---|---|---|
| Bubble の API Connector で `capture=false` の boolean 送信がうまくいかない | +1〜2日（Bubble の仕様検証） | 中 |

> ただし API Connector のパラメータ設定やワークフローの条件分岐は検証に時間がかかりがち。
