## 1. はまりポイント集（よくあるミス）

### はまりポイント 1: `capture=false` の指定忘れ 【CRITICAL】

```
❌ ダメな例:
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  currency: jpy
  ← capture パラメータなし（デフォルト true = 即時課金！）

✅ 正しい例:
POST /v1/charges
  customer: cus_xxx
  amount: 10000
  currency: jpy
  capture: false        ← これを必ず指定！
```

**被害:** お客さんの予約確定時に即座にお金が引き落とされる。
**対策:** Bubble のワークフローで `capture` フィールドに `false` をハードコーディング。

---

### はまりポイント 2: charge_id の保存忘れ 【CRITICAL】

```
❌ ダメな例:
  オーソリ実行 → レスポンス受け取る → charge_id を保存しない
  ↓
  キャプチャ時: charge_id がないのでキャプチャできない！！

✅ 正しい例:
  オーソリ実行 → レスポンスの id を予約の charge_id フィールドに即座に保存
```

**被害:** キャプチャ不可 = お金を回収できない。最悪のシナリオ。

> **実際にこのバグが起きている！**
> 現行システムの延長決済で `__charge_id` の保存漏れが発生中。延長分の返金ができない状態。
> 同じミスを絶対に繰り返さないこと。

---

### はまりポイント 3: `expiry_days` の上限は60日 【HIGH】

```
❌ ダメな例:
  expiry_days: 90    ← エラーにはならないが、60日を超える値は無視される

✅ 正しい例:
  expiry_days: 60    ← 最大60日
```

**被害:** 予約日がオーソリから60日以上先だと、ライド当日にキャプチャしようとしても失効済み。
**対策:** 営業カレンダーの予約可能範囲を60日以内に制限する。

---

### はまりポイント 4: 海外カードのオーソリ有効期限は7日！ 【HIGH】

```
日本発行カード: expiry_days 最大60日
海外発行カード: expiry_days 最大 7日 ← ★ 要注意！
```

**確認方法:** テストカード `4000000900000003`（`is_jp=false`）で検証可能。

---

### はまりポイント 5: キャプチャ時の金額変更に要注意 【HIGH】

**ルール:**
- キャプチャ時の金額 ≦ オーソリ時の金額 → OK
- キャプチャ時の金額 > オーソリ時の金額 → NG（エラー）

```
【推奨パターン】
  予約時:     オーソリ 10,000円（charge_id = ch_001）
  ライド開始: キャプチャ 10,000円（ch_001 をキャプチャ）
  延長発生:   新規課金  3,000円（capture=true で別チャージ ch_002 を作成）
```

---

### はまりポイント 6: テスト環境で本番キーを使わない 【CRITICAL】

```
❌ ダメな例:
  テスト時に sk_live_xxxx を使う
  → テストカードが使えない！ 本物の課金が走る！

✅ 正しい例:
  テスト時は sk_test_xxxx / pk_test_xxxx を使う
```

---

### はまりポイント 7: オーソリ失効後のキャプチャ 【HIGH】

```
❌ ダメな例:
  5月1日: オーソリ（expiry_days=60）
  7月5日: キャプチャ（65日後） → エラー!

✅ 正しい例:
  5月1日: オーソリ（expiry_days=60）
  6月25日: キャプチャ（55日後） → 成功
```

**対策:** キャプチャ前に `GET /v1/charges/{id}` で状態確認。失効済みなら再オーソリ。

---

### はまりポイント 8: 二重キャプチャ 【MEDIUM】

**対策:** キャプチャ前に `payment_status` を確認し、`"authorized"` の場合のみ実行。ボタンの連打防止も設定。

---

### はまりポイント 9: Platform API での tenant 指定忘れ 【HIGH】

RINCLE は Marketplace型の Platform API を使っているため、`tenant` と `platform_fee` は**常に必須**。

---

### はまりポイント 10: Webhook の `charge.captured` イベント 【MEDIUM】

即時課金でもオーソリ→キャプチャでも `charge.captured` は発火する。区別が必要な場合は独自の `payment_status` で管理すること。

## 2. テスト手順

### テストカード一覧（正常系）

| カード番号 | ブランド | 用途 |
|-----------|---------|------|
| `4242 4242 4242 4242` | Visa | **基本テストに使用** |
| `5555 5555 5555 4444` | Mastercard | ブランド別テスト |
| `3530 1113 3330 0000` | JCB | ブランド別テスト |

- 有効期限: 未来の任意の年月（例: `12/30`）
- CVC: 任意の3桁（例: `123`）

### テストカード一覧（異常系）

| カード番号 | エラー | テスト内容 |
|-----------|--------|----------|
| `4000 0000 0000 0002` | `card_declined` | カード利用不可 |
| `4000 0000 0008 0319` | `card_declined`（Charge時） | **トークンは成功、課金時にエラー** |
| `4000 0000 0008 0202` | `card_declined` | 10,000円超で与信枠超過 |
| `4000 0009 0000 0003` | 海外カード | **オーソリ有効期限が7日に制限** |

### テストシナリオ

#### シナリオ A: 正常フロー（オーソリ → キャプチャ）

1. テストカード `4242424242424242` でカード登録
2. 予約を作成・確定 → オーソリ実行
3. 確認: `charge_id` が保存、`payment_status` が "authorized"、Pay.JP管理画面で `captured=false`
4. ライド開始 → キャプチャ実行
5. 確認: `payment_status` が "captured"、Pay.JP管理画面で `captured=true`

#### シナリオ B: キャンセルフロー（オーソリ → 解放）

1. 予約を作成・確定（オーソリ実行）
2. 予約をキャンセル
3. 確認: `payment_status` が "cancelled"、Pay.JP管理画面で `refunded=true`

#### シナリオ C: カードエラーフロー

1. テストカード `4000000000080319` でカード登録（登録自体は成功）
2. 予約を作成・確定 → オーソリ実行 → `card_declined` エラー
3. 確認: エラーが分かりやすく表示、予約がキャンセルまたは保留、`charge_id` は未保存

#### シナリオ D: 延長決済フロー

1. 正常フローでオーソリ → キャプチャまで完了
2. 延長操作を実行
3. 確認: 延長分は別の `charge_id` で新規課金、`__charge_id` に保存済み、返金が可能

## 3. エラーコード一覧と対処法

### オーソリ時に発生しうるエラー

| エラーコード | 意味 | ユーザーへの表示例 | 対処法 |
|---|---|---|---|
| `card_declined` | カード利用不可 | 「このカードはご利用いただけません。別のカードをお試しください」 | 別カードを登録してもらう |
| `expired_card` | 有効期限切れ | 「カードの有効期限が切れています。新しいカードを登録してください」 | カード再登録 |
| `insufficient_fund` | 与信枠不足 | 「カードの利用限度額を超えています」 | 別カードまたはカード会社に連絡 |
| `processing_error` | Pay.JP側エラー | 「一時的なエラーが発生しました。しばらくしてからお試しください」 | リトライ |

### キャプチャ時に発生しうるエラー

| エラーコード | 意味 | 対処法 |
|---|---|---|
| `already_captured` | 二重キャプチャ | payment_status を確認、すでに captured なら何もしない |
| `charge_expired` | オーソリ失効 | 再オーソリを取り直す → 成功したらキャプチャ |
| `invalid_amount` | 金額超過 | オーソリ時の金額以下でキャプチャする |

## 4. チェックリスト

### 実装前チェック

- [ ] テスト環境の API キーが `sk_test_` / `pk_test_` であることを確認
- [ ] API Connector に `Charge_capture`（キャプチャ用）を追加した
- [ ] `Charge_by_car_id` に `capture` と `expiry_days` パラメータを追加した
- [ ] 予約テーブルに `payment_status` フィールドを追加した

### 実装中チェック

- [ ] 予約ワークフローで `capture=false` を指定している
- [ ] 予約ワークフローで `expiry_days=60` を指定している
- [ ] オーソリ成功後に `charge_id` を予約に保存している
- [ ] オーソリ成功後に `payment_status` を `"authorized"` に更新している
- [ ] ライド開始ワークフローで `Charge_capture` を呼び出している
- [ ] キャプチャ成功後に `payment_status` を `"captured"` に更新している
- [ ] キャンセル時の条件分岐（authorized / captured）が正しい
- [ ] 延長料金は別チャージで処理している（オーソリ金額を超えない）
- [ ] `tenant` と `platform_fee` を必ず指定している

### テスト完了チェック

- [ ] シナリオ A（正常フロー）が成功する
- [ ] シナリオ B（キャンセルフロー）が成功する
- [ ] シナリオ C（エラーフロー）でユーザーに分かりやすいメッセージが出る
- [ ] シナリオ D（延長決済フロー）が成功する
- [ ] Pay.JP 管理画面で charge の状態が正しいことを確認
- [ ] 海外カード（`4000000900000003`）でのテストを実施

### リリース前チェック

- [ ] API キーを本番キー（`sk_live_` / `pk_live_`）に切り替えた
- [ ] 営業カレンダーの予約可能範囲が60日以内に制限されている
- [ ] エラーメッセージがユーザーフレンドリーであることを確認
- [ ] 管理者へのエラー通知が設定されている

## 5. 開発見積もり

### 合計: 約2週間（80時間）

3段階バリデーション + テスト込み。

### Phase 1: 実装

| タスク | 目安 |
|---|---|
| STEP 1: 予約時¥50オーソリ + CVC検証 | 1〜2日 |
| STEP 2: バッチオーソリ + メール通知 | 2〜3日 |
| STEP 3: 当日キャプチャへの切替 | 1日 |
| **小計** | **4〜6日** |

### Phase 2: テスト・検証

| タスク | 目安 |
|---|---|
| 各STEPの単体テスト | 1〜2日 |
| 通しテスト（予約→3日前→当日） | 0.5〜1日 |
| E2Eテスト更新 | 0.5日 |
| バグ修正・手戻り（バッファ） | 1〜2日 |
| **小計** | **3〜5日** |

### リスク要因

| リスク | 影響 | 発生確率 |
|---|---|---|
| Bubble の API Connector で `capture=false` の boolean 送信がうまくいかない | +1〜2日 | 中 |
| 既存ワークフローの依存関係が想定より複雑 | +1〜2日 | 中 |
| 営業カレンダー60日制限の UI 変更が必要 | +1日 | 高 |
| 海外カード対応（7日制限）の追加要件が入る | +0.5日 | 低 |

> **ポイント:** Bubble での作業なのでコードを書くよりは設定変更が中心。
> ただし API Connector のパラメータ設定やワークフローの条件分岐は検証に時間がかかりがち。
> **テスト期間（Phase 2）は絶対に削らないこと。**
