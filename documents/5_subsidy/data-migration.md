# データ移行 — Bubble版RINCLEから新システムへ何を移すか

- 作成: 2026-09-16。補助金事業（`roadmap.md`）でBubble版を作り直すにあたり、Bubbleのデータを新システムへ移す範囲と手順を決める
- 根拠: Bubbleのアプリ書き出し `rincle-test/rincle.bubble`（データ型34種）と、2026-06-11の本番書き出し（`4_growth/01_strategy/context/`・gitignore対象）
- HTML版（クライアント向け・このmdが正本）: `98_presentations/subsidy/data-migration.html`
- 決済の前提: **Pay.jpを継続**する場合を基本に書く。Stripeへ載せ替える場合の差分は§4に併記

> **結論**
> - 移すのは**6区分**: 店舗 / 営業日・貸出日 / 自転車 / 料金 / 会員 / 予約。2026-06-11時点で店舗54店・自転車369台・会員146人・予約121件
> - **Pay.jpはIDを移すだけ**。店舗の`tenant_id`・会員の`customer_id`・予約の`charge_id`を新DBに持っていけば、店舗の再申請・運営の再審査・利用者のカード再登録は発生しない
> - **移せないのはパスワードだけ**。公開時に全会員へ再設定の案内を出す
> - 画像はBubbleの置き場からダウンロードして新システムに入れ直す（Bubble解約で消えるため）
> - 日程は10/26〜11/6にスクリプト、11/9〜11/13にリハーサル、**11/23の納品時点で実データ入りのステージング**を渡す。公開時に差分だけ再移行

## 1. 移すもの（6区分）

| 区分 | Bubbleの型 | 件数（2026-06-11） | 中身 | 注意 |
|---|---|---|---|---|
| 店舗 | shop | 54店 | 店舗名・住所・最寄駅・アクセス・紹介文・連絡先・画像・都道府県・前日貸出の可否・現地払いの可否 | Pay.jpの`tenant_id`・申請フォームURL・審査状態（brand_status）をそのまま持つ |
| 営業日・貸出日 | __20_business_hour、shop_holiday、bicycle_exception、option_exception | 未確認（6/11書き出しに含まれず） | 曜日ごとの営業時間 / 定休日・臨時休業・臨時営業（日付範囲） / 自転車ごと・オプションごとの貸出不可日 | 切替日以降の分だけ移す。shop_holidayの「レンタル可能な自転車リスト」は計算結果なので**コピーしない**（§6） |
| 自転車 | Bicycle | 369台 | 名前・ブランド・サイズ・色・シリアル・電動か・最大貸出日数・料金（4時間〜30日・延長1時間・延長1日）・画像・表示順 | 「__is_archive」が立っているものは移さない |
| 料金 | Price_menu、Option、Sub_Option | 316行（bike-option） | 店舗ごとの料金表 / オプション（ヘルメット等）とその料金・数量 | 自転車にも料金表にも同じ料金項目がある。新DBでどちらを正にするか設計で決める（§6） |
| 会員 | User、rider_info | 146人（ユーザー91・加盟店54・管理者1） | 氏名・かな・生年月日・身長・電話・住所・郵便番号・メール・権限・所属店舗・Pay.jpの`customer_id`・最終利用日 | **パスワードは移せない**。rider_info（予約時に入力した乗る人の情報）は予約に紐づけて移す |
| 予約（過去分と未来分の全件） | reservation、reservation_detail、reservation_option、sales_record | 121件 | 予約番号・店舗・利用者・貸出日・返却日・延長・合計金額・手数料・支払方法・状態 / 明細（自転車・料金表・乗る人）/ 付けたオプション / 月次の売上記録 | Pay.jpの`charge_id`（本決済・延長・返金）を必ず持つ。返金と効果報告の集計に使う |

### 移した方がよいもの（運営コンテンツ）

News、Banner、FAQ、q&a_category、contact（問い合わせ履歴）、notification。件数が少なければ、運営が新システムで入れ直す方が早い。10/26のスクリプト作りの前に件数を見て決める。

## 2. 移さないもの・移せないもの

| 分類 | 対象 | 理由 |
|---|---|---|
| 移さない | Prefecture、holidays、holiday_master、select_prefcture | マスタ。新システム側で定義し直す |
| 移さない | access_log、log（webhook_event）、__FV、__maintenance、__27_reservation_count | ログと作業用。アクセス解析はGA4に置き換わる |
| 移さない | 「- deleted」の付いた廃止項目、`__`始まりの旧項目で新項目に置き換わっているもの | 新旧の対応表（§5）で1件ずつ判定する |
| 移さない | shop_holidayの「__レンタル可能な自転車s」 | 予約が入るたびにBubbleが書き換えている計算結果。コピーすると予約データと二重管理になる |
| 移せない | パスワード | Bubbleが暗号化して持っていて取り出せない。公開時に再設定メール |
| 移せない（Stripeにする場合のみ） | カード情報 | Pay.jp側にあり他社へは移せない。Pay.jp継続なら`customer_id`を移すだけで登録済みカードはそのまま使える |

## 3. Pay.jpの扱い

テナント（店舗ごとの決済口）と顧客（会員のカード）はBubbleではなく**PEDALSTANDARD社のPay.jpアカウントの中**にある。新システムが持つのはそのIDだけ。

| 移すID | どこにある | 何に使う |
|---|---|---|
| `tenant_id`（ten_…） | shop | 決済時に「どの店舗に払うか」を指定する。54店全てに入っている（全店が審査通過済み） |
| `customer_id`（cus_…） | User | 登録済みカードでの決済。カード再登録が不要になる |
| `charge_id`・`ex_charge_id`・`cancel_charge_id` | reservation | 返金、延長決済の照合、売上集計 |

### Pay.jp側でやること（増永さん）

1. Pay.jpの管理画面でAPIキー（秘密鍵・公開鍵）を確認して弊社に渡す。Bubbleに入っているものと同じアカウントであることを確認する
2. Webhookの送り先URLを新システムのものに差し替える（テナントの審査結果通知`tenant.updated`などを受けるため）。切替日に行う

### 店舗の再申請が必要になる場合（今回は該当しない）

- Pay.jpのアカウント自体を作り直す
- Pay.jpのまま「テナント型→単一アカウント型」に契約を変える（`payjp-vs-stripe-comparison.md`のルートB）
- Stripe Connectのように店舗ごとの口座を作る方式にする

### Stripe集約モデルにする場合の差分

`tenant_id`は不要になる（PEDALSTANDARD社が一括で受けて店舗へ月次振込）。会員のカードは移せないので公開時に全員再登録。店舗の振込先口座を新たに集める。6/19の決定はこちらだが、11月の納品に収めるならPay.jp継続、Stripeは12月以降の別工程が現実的（`roadmap.md`§3 論点3）。

## 4. 画像の扱い

店舗画像・自転車画像・会員画像はBubbleのファイル置き場（S3のURL）にある。BubbleのCSV書き出しにはURLしか入らない。

- 移行スクリプトでURLから画像を取得して新システムの置き場（Supabase Storage等）に入れ直し、新URLをデータに書き込む
- Bubbleを解約すると元の画像が消えるので、この工程は省けない
- 取得できなかった画像は一覧にしてPEDAL社に渡し、手で差し替えてもらう

### 照合のしかた

- 件数: 型ごとにCSVの行数と新DBの件数が一致すること
- 金額: 予約の合計金額・手数料の合計がBubbleと一致すること（売上集計に直結）
- 画面: 店舗一覧・自転車一覧・予約一覧・マイページを開いて、代表3店舗分を目で確認

## 6. 設計で決めること

| 論点 | 現状 | 弊社の見立て |
|---|---|---|
| 自転車と料金表の二重持ち | Bicycleにも「1日料金・延長料金」があり、Price_menuにも同じ項目がある | 新DBでは料金表を正にして、自転車は料金表を参照する。移行時にBicycle側の料金は料金表に寄せる。7月のDB設計に答えがあればそれに従う |
| Userの中に会員・店舗担当・管理者が混在 | 権限（Right）で区別している | 会員と店舗スタッフを別テーブルにするか、権限で分けたままにするかを機能設計①で決める。移行スクリプトはどちらにも対応できる |
| 空き状況の持ち方 | shop_holidayに「その日に借りられる自転車のリスト」を保存している | 保存せず「自転車一覧 − 予約済み − 貸出不可日 − 休業日」で毎回計算する。二重管理をなくす |
| 予約の過去分をどこまで移すか | 121件（6/11時点） | 全部移す。効果報告（3年間）の予約件数・売上の元データになる |
| 運営コンテンツ（News・FAQ等） | 件数未確認 | 少なければ運営が入れ直す。10/26前に件数を見て決める |
