3. 仕様まとめ

  • 曜日テンプレート（営業カレンダー（曜日））で、月～日＋祝日の8パターンの営業時間・営業/休業を設定
  • 日付実体（営業カレンダー（日付））が曜日テンプレートから自動生成され、個別の日の営業状態・時間を管理
  • 日付実体には「レンタル可能な自転車s」リストがあり、その日に貸し出せる自転車を管理
  • Time option set は10分刻み（0:00～23:50）で営業開始/終了を指定
  • 予約処理で実際に参照されるのは「営業カレンダー（日付）」側のレコード
  • Sub_Option テーブルに number0~5 として営業カレンダー（日付）のリストが紐づいており、オプション品の在庫管理にも利用

4. 改善した方が良い点

(a) 曜日マッチングが文字列比較に依存 リスク

format_date("ddd曜") で日付を「月曜」「火曜」等にフォーマットし、曜日 option set の display と一致判定している。

問題: ロケール依存。Bubble サーバーのロケール設定が変わると壊れる。

改善案: 曜日番号（1-7）での比較に変更する。

(b) 祝日の扱いが不完全 バグ疑い

曜日 option set に「祝日」が定義されており、holidays テーブルや 日付データ defaults.holiday フラグも存在する。

問題: 日付レコード生成時に祝日判定→祝日テンプレート適用するフローが見当たらない。祝日テンプレートを設定しても反映されていない可能性。

改善案: 日付レコード生成時に holidays テーブル or defaults.holiday を参照し、祝日なら祝日テンプレートを優先適用するロジックを追加。

(c) 日付データ系テーブルが冗長 重複

日付データ defaults、日付データ 追加用、Holidays の3テーブルが類似の役割で分散。

日付データ 追加用 はカラム名が hliday（typo: holiday の o 抜け）。

改善案: 1テーブルに統合し、typo も修正。

(d) 初期登録で約365日分が全て「休業」で作成される 仕様課題

shop_form の SignUp 時に 営業日付_初期登録_list が呼ばれ、Defaults の全日付（約365日分）に対して営業状態=休業, startTime/endTime=空 で一括作成される。曜日テンプレートは参照しない。

問題 1: ショップがオンボーディングで曜日テンプレートを設定しても、既に作成済みの約365件には反映されない。

問題 2: リカーリング C（営業カレ作成1~4）は「レコードが既にあればスキップ」するため、休業レコードが上書きされることもない。

問題 3: 結果として、ショップは365日分を1日ずつ手動で営業に変更する必要がある。

改善案: 曜日テンプレート変更時に、未来の日付レコードを曜日に応じて一括更新する仕組みを追加。または初期登録の順序を変え、曜日テンプレート設定後に日付レコードを生成する。

(e) B（日次生成）と C（定期補充）が実質的に二重処理 パフォーマンス

B は「毎日1日分を全店舗に作成」、C は「翌年分の歯抜けを全店舗に補充」。C があれば B のカレンダー作成は不要（逆も然り）。

問題: 二重実行で WU を無駄に消費。また B で Defaults が作られない日があると C も空振り（Defaults の日付がないと C のリストに出てこない）。

改善案: B は Defaults 延伸のみに限定し、カレンダー作成は C に一本化する。

(f) リカーリングの冪等性の懸念 リスク

営業カレ作成4 は「既存チェック → なければ作成」をしているが、タイミング次第で重複作成のリスクがある。

改善案: ユニーク制約（店舗+日付）や、作成後の重複チェック処理を追加。

(g) business_hour がテキスト型 曖昧

User テーブルの business_hour が text 型。構造化された営業カレンダーとの使い分けが不明確。

改善案: 表示専用なら OK。ロジックに使われているなら構造化データに統一すべき。

(h) 予約上限59日なのに365日分を生成している パフォーマンス過剰

予約UIの日付ピッカーの上限は以下の通り:

項目制約実質上限
貸出日plus_days(31)最大31日先
返却日plus_days(59)最大59日先（≒約2ヶ月）

問題: 予約は最大59日先までしかできないのに、営業カレンダー（日付）は Defaults の全期間（約365日先）分を一括作成している。約300日分のレコードが完全に無駄。

新規店舗登録時だけでなく、リカーリング B/C も翌年分まで先行生成しており、全店舗で不要なレコードと WU を消費し続けている。

改善案: 生成範囲を予約上限+バッファ（例: 70日先）に制限する。これだけで生成レコード数が約1/5になり、WU を大幅に節約できる。
