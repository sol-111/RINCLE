# html-doc-design スキルの説明書

クライアント向けHTML資料を作るためのClaude Codeスキル。主の様式は「読めるデッキ」（BCGの報告書と同じ16:9の1枚を単位に、主張の見出し・図表・出典を1枚ごとに完結させる）。手順書・定型レポート・用語集だけ「誌面」（縦に読むページ）で組む（2026-09-29）。
この説明書は、スキルの中身がどうなっているか・どう使うか・社内にどう配るかをまとめたもの（同じ内容のHTML版が `guide.html`。ブラウザで読むならそちら）。

## そもそもスキルとは

Claude Codeの「スキル」= **ただのファイルの束**。`~/.claude/skills/<スキル名>/` にフォルダを置くだけで登録され、サーバー登録や設定画面は一切ない。

動く仕組みは3段階:

1. `SKILL.md` 冒頭の **description（説明文）だけは、どの案件でClaudeを開いても常に見えている**（名刺のようなもの）
2. 「HTML資料を作って」「デザインを統一して」など該当する依頼が来ると、Claudeが自分でこのスキルを開き、`SKILL.md` の本文（ルール）が読み込まれる
3. 残りのファイル（CSS・雛形・見本）は、本文の案内に従って必要な時だけ読まれる

つまり普段は説明文1行分しか場所を取らず、必要な時だけ載る省エネ構造。確実に発動させたい時はチャットで `/html-doc-design` と打つ。

## このデザインシステムの考え方

**コンサルの成果物の型で、1枚ごとに主張が完結する資料を組む。部品は「伝えたいことの形」で1つに絞って選ぶ。**（2026-09-29に決め直した）

| 様式 | 位置づけ | 使う資料 |
|---|---|---|
| 読めるデッキ | 既定 | 提案・報告・分析・比較検討・方針・見積（事前に送って読んでもらい、打合せでも映す） |
| 誌面 | 付録 | 手順書・定型の月次レポート・用語集・APIリファレンス（上から順に読む・長さが決まらない） |
| 画面UI | 付録 | 資料の中でアプリの画面を再現するときだけ |

選び方は3段: ①器を決める（迷ったら読めるデッキ）→ ②伝えたいことの形で gallery.html の章を引く（文法・器・答え・数字・比べる・流れと時間・論理・補足と根拠）→ ③章の中で1つに絞る（SKILL.md の選択表）。同じ部品がデッキにも誌面にも置ける。

部品の多くは、経産省の委託調査報告書29本（BCG・NRI・みずほR&T・トーマツ・デロイト・ADLほか）から取り込んだ型。特定の会社に寄らず、「1枚で答え・根拠・前提に当たれるか / 誤読しないか / 作り手が再現できるか」で選んでいる（経緯は decisions.md）。

## 中身のファイルと役割

```
~/.claude/skills/html-doc-design/
├── SKILL.md       … ルールブック。様式の使い分け+原則+読めるデッキ+部品の地図+誌面のページ構造+検証手順
├── decisions.md   … 規約を「なぜそう決めたか」の経緯・教訓（普段は読まない。変えたくなった時に）
├── template.css   … 資料部品の核CSS。カラートークン・ヒーロー・章ナビ・表・チャート・
│                     図解・スライド枠・演出まで（納品ページにコピーして使う）
├── parts.css      … 画面UIの部品CSS（ボタン・入力欄・モーダル・かんばん等）。
│                     資料の中でアプリの画面を再現する時だけ足す
├── snippets.html  … 各部品のHTML雛形集（gallery.htmlと同じ章の順・コピーして使う）。SVGスプライト・スクリプト2種も収録
├── gallery.html   … 資料部品の見本 =「見た目の正本」。伝えたいことの形で8つの章＋付録A 誌面
│                     （template.cssをlink参照しており、CSSを直せば自動で追随）
├── gallery-ui.html … 画面UIの部品（parts.css）の見本。アプリ画面を再現する時だけ使う
├── deck.html      … 読めるデッキの器（一覧表示が既定・Pキーで送り・PDF化）
├── shell.html     … 複数ページをまとめるSPAシェルの雛形（サイドバー+iframe）
├── lint.py        … 規約の検査プログラム。ページを書いたら必ずかける
├── guide.html     … 人間用の説明書（この説明書のHTML版。README.mdを直したら同期する）
├── README.md      … この説明書（Claudeは読まない。人間用）
└── review/        … レビューの道具（内容レビューの依頼文 content-prompt.md・初見レビューの
                      撮影スクリプト shoot.mjs・依頼文 prompt.md・手順 README.md）
```

- **SKILL.md** … 「何を守るか」。BCGの作法（ゴシック1本・緑の見出し・黒を使わない）・罫線と余白・数字には出典・部品の優先度、など
- **template.css / parts.css** … 「どう見えるか」。`:root`のトークン（アイビスの緑・灰の段・紺・オレンジ・役割色）を先頭に集約。**色はアイビスに固定**（案件ごとに差し替えない。2026-09-29）
- **snippets.html** … 「どう書くか」。部品ごとのコピペ用HTML
- **gallery.html** … 「どう見えるべきか」の正本。迷ったらブラウザで開いて見比べる（章は 文法・器・答え・数字・比べる・流れと時間・論理・補足と根拠）

**部品や規約を追加・変更したら5点セットで更新する**: template.css（実体）→ snippets.html（雛形）→ gallery.html（見本）→ SKILL.md（ルール）→ lint.py（機械チェックできる規約のみ）。CSSだけ直して雛形・見本を忘れるのが典型的な漏れ方。

## 使い方

### ふだんの使い方
Claude Codeでそのまま頼むだけ（提案・報告は読めるデッキ、手順書・定型レポートは誌面で組まれる）:
- 「この調査結果を、いつものデザインでHTML資料にして」
- 「このページをデザインシステムに合わせて刷新して」
- 書き上がったら `python3 lint.py <出力先>` で検査される（Claudeが自分でかける）
- 効かない時は `/html-doc-design` を打ってから頼む

### 色について（2026-09-29 から固定）
色はアイビスの緑に固定した（主色=ロゴの葉 #72B000・文字の緑 #4E8A00・当社の独自提案=オレンジ #F87830）。案件ごとのブランド色への差し替えはしない。どの案件の資料も「アイビスが作った資料」として同じ見た目になる。

### デザインを変えたくなった時（更新の流れ）
1. gallery.htmlをブラウザで開き、変えたい部品を指差して相談する（大きな変更は、Claudeが今の部品と新しい部品を左右に並べた対照のHTMLを作って見せる）
2. 方向が決まったら「スキルに反映して」と頼む → Claudeが5点セットを書き換える
3. リポジトリ側の既存ページがある場合は「全ページに反映して」で移植。リポジトリにスキルを同梱している案件では、更新後にリポジトリ側へコピーする

## 社内展開のやり方

スキルはただのフォルダなので、**配る=フォルダをコピーする**。置き場所で使える範囲が変わる:

| 置き場所 | 使える範囲 | 向いている使い方 |
|---|---|---|
| `~/.claude/skills/html-doc-design/` | その人の全案件 | 個人の標準装備にする |
| リポジトリの `.claude/skills/html-doc-design/` | そのリポジトリを開いた人全員 | **チーム展開はこちら**。gitで共有され、pullした人に自動で配られる |

チーム展開の手順（例）:

```bash
mkdir -p .claude/skills
cp -r ~/.claude/skills/html-doc-design .claude/skills/
git add .claude/skills && git commit -m "docs: HTML資料デザインシステムをスキルとして同梱"
```

これでリポジトリをpullしたメンバーのClaude Codeにも同じスキルが出る。個人版とリポジトリ版が両方ある場合、そのリポジトリ内ではリポジトリ版が優先される。
